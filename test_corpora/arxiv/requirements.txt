# The arXiv rung's environment — `~/venvs/arxiv`, Python 3.12. Not `~/venvs/ingest`, which is the
# geographic rungs' DuckDB and PyArrow and needs none of this.
#
# Python is a **consumer** here and never a component. This writes files; nothing in it sits on a
# request path, produces a served artifact, or belongs to any trusted computing base.
#
# Unpinned, on `reference/pyproject.toml`'s argument: every use is of a long-stable API surface, and
# a lockfile would be a maintenance obligation bought for nothing. The ones that matter are named
# with a reason rather than a version — and the one that is pinned says why.

pyarrow
numpy
scikit-learn

# **UMAP is umap-learn on the CPU**, not cuML. The GPU projection that produced
# `data/geometry.parquet` is not bit-reproducible even under a fixed seed; umap-learn is, when it
# is given a `random_state` — which also drops it to one thread. See the README's three geometries.
umap-learn

# **HDBSCAN is the `hdbscan` package, not scikit-learn's implementation**, for one reason: it
# exposes `condensed_tree_`, which *is* the hierarchy. scikit-learn's returns a flat labelling and
# reconstructing the tree from a single-linkage matrix would be reimplementing the algorithm's own
# output, and a place for this pipeline to disagree with the literature.
hdbscan

# ---------------------------------------------------------------- the optional Toponymy stage

# **Toponymy names the clusters**, through its own layered HDBSCAN (fast_hdbscan) and a chat model
# behind an OpenAI-compatible endpoint. Pinned: the 0.5.3 wheel on PyPI ships without its
# `toponymy.tools` package and cannot be imported. Lift the pin when a later release imports.
toponymy==0.5.2
openai

# The text encoder Toponymy's keyphrase step needs, and it has to be the corpus's own embedding
# model (BGE-large-en-v1.5) for the step to mean anything. CPU torch is enough — a few tens of
# thousands of short phrases — and the GPU is where the language model lives.
sentence-transformers
torch
