Part V — Time and change

14. Ingest: entity space only grows

A real corpus moves: documents arrive, documents are withdrawn, and the clearance attached to a document changes without the document changing at all. Each has to be reconciled with masks computed before it happened. What makes that tractable is a deliberate restriction on what ingest may touch.

Entity space is append-only — invariant I9. Ingest appends entity IDs and appends postings to the term index. It never reorders, never rewrites, and never invalidates anything expressed in entity space: masks, node memberships and generating sets all remain valid, merely incomplete. That distinction is the whole of the design. An invalidated mask must be discarded and rebuilt; an incomplete one has a boundary, and a boundary can be recorded and patched. Target ingest visibility latency is seconds to minutes, and it is not coupled to any credential cadence, because the model has none.

The churn lives in row space instead, where new items interleave arbitrarily into the existing Morton ranking and a correct in-place insert would renumber a large fraction of the slice. That is why the permutation between entity IDs and row positions exists (invariant I4): row order may be rewritten wholesale at a merge, because nothing durable depends on it.

Append-only does not mean order-free. Within a batch, entity IDs are assigned sorted by term signature, so postings form long runs inside the batch's ID range: created-order assignment yields run lengths of 1.00–1.26 against a 1.000 random baseline, which is to say nothing, while signature-sorted assignment buys 8.9–36.7× on posting storage and up to 130× on union cost at equal coverage. Assigning IDs in Morton order instead is prohibited: it would give permission-space IDs spatial meaning, turning the ID gap between two visible points into an estimate of how much unauthorised data lies between them. Signature ordering is safe only because entity IDs never cross the trust boundary (I10) — and because I9 makes assignment permanent, it ships in the first implementation of the allocator or not at all.

The log and the ack

Each partition has one write-ahead log with a single appender, its lifecycle thread; records are append-only, length-prefixed and individually CRC'd. That thread owns every mutation decision but does only cheap work itself — drain the command queue, append and fsync, swap pointers — while everything else runs on a background pool. The queue has a priority lane for deny-disposition changes, so a compaction publish or a stalled object-store upload can never queue a suppression behind seconds of IO: deny visibility latency is bounded by queue-front plus fsync, and nothing else.

The ack ordering is load-bearing: WAL fsync, then the overlay and generation swap, then the 200. The swap takes nanoseconds and sits before the ack, so a caller's own next request always observes its own accepted change; the window it leaves — after fsync, before the swap — recovers by replay and was never acked.

Recovery replays from the last flush marker, and a CRC failure is read by position. In the unsynced tail it truncates the log — those records were never acked. At or below the last fsync point the failure is corruption of acked state, possibly including denies, and recovery fails closed until an operator restores from the bundle and the object store; truncate-at-first-bad-CRC applied mid-log would silently drop acked denies. Exhaustion follows the same principle: the ingest 429 threshold sits strictly below the log's hard bound so change records always have room to land, and if an append genuinely fails the deny is applied to the in-memory overlay and swapped — visible immediately — while the response is a 500 with an alarm. Never a 200 without fsync, never a silent drop, never a refusal that leaves the item visible.

Buffer, watermark, overlay

Arrivals land in an in-memory buffer. A flush policy — size or age, whichever trips first — turns that buffer into an immutable on-disk segment, so segment count is governed by the flush interval rather than by the arrival rate. Every mask fragment carries an entity high-water mark: a fragment built at watermark W is authoritative below W, and entities at or above W are new and not yet folded in. Flushing advances W by OR-ing in the flushed segment's contribution for the token's already-known satisfied terms — a small, monotone patch rather than a rebuild.

Changes to items already below W go to the overlay, which holds the items in flux: those whose predicate changed, those deleted, and those administratively suppressed. Each entry carries a disposition — evaluate, meaning test its current term set against the token's, or deny, meaning invisible regardless — and carries its term set inline. The disposition is what lets one mechanism cover both a predicate change and an administrative suppression. The live set is the overlay together with every entity at or above W, and evaluating it needs no index at all: an item's term set is a handful of IDs, so visibility is a set intersection against the token's satisfied terms — microseconds for tens of thousands of items — and the set stays bounded by the change rate times the interval before masks are naturally rebuilt. A deletion is a tombstone in this frame: remove the entity from the term index, add a deny entry, notify the caller of the labels affected, and drop the row at the next compaction. The ID is never recycled.

Segments, merges, compaction

A tile resolves to one contiguous range per live segment, so query cost is linear in segment count and segment count must be bounded. Merge policy is structured on established lines rather than run as a scheduled job: a floor size, so a tail of tiny segments cannot dominate decisions; a maximum merged-segment size, so no merge becomes an unbounded rewrite; and a separation of the reasons to merge — natural tiering, forced compaction, and tombstone reclamation on a deletes-percentage trigger. Re-ranking is a decorator on that policy rather than a phase of its own — reorder only merges above a minimum document count, always reorder on forced merges — so the Morton re-rank becomes a continuous property of large merges rather than a scheduled cliff. The reference points taken from a widely-deployed policy are ten segments per tier, a 5 GB maximum merged segment, a 2 MB floor, a 20% deletes threshold, and reordering above 218 documents.

Compaction snapshots a generation, folds the snapshot-covered posting deltas, tombstones and evaluate entries into the base postings, rewrites the permutation, tile table, candidate lists and columns, publishes under a new segment-set version, and lets in-flight requests drain. What it must not fold is specified as carefully as what it folds: segments and deltas flushed after the snapshot, tombstones accepted after the snapshot, the active suppression set, and all unfolded overlay entries are carried forward verbatim. That tombstone clause is a correction — an earlier rule covered only segments and deltas, and folding away a post-snapshot tombstone while the entity survives in the folded base is fail-open.

15. Denial: generations, pins, and three retirement rules

All of a partition's serving state hangs off a single atomically swappable pointer to an immutable generation: the segments and their version number, the postings view, the watermark W, and the overlay with its own version number. The two version numbers move for different reasons. The segment-set version moves on flush and compaction — row-space and postings shape. The overlay version moves on every accepted change batch — security state. Every mutation builds a new generation sharing its unchanged parts by reference count; a change-only generation is two small allocations, which is what makes a suppression cheap enough to apply synchronously.

One ordering rule governs how a request reads that state, and it is tested rather than assumed: a request thread loads the generation pointer exactly once, at request start, before acquiring any fragment or cache entry — overlay resolution happens-before fragment acquisition. That is what makes fragment eviction safe while a request still holds a fragment: the request's own overlay still carries any deny the ledger has since retired. An implementation that refreshes a fragment mid-request leaks in the window between eviction and retirement.

Pins

A pin is a counted reference to a generation; superseded generations sit on a drain list until the last holder lets go. The reclaim ordering is deliberate — remove the entry from the drain list, then verify the strong count is one, then reclaim — because verify-then-remove is a use-after-free that review caught. A racing pin resolution that misses the removed entry gets a 410 pin-expired, which is the correct answer.

What a pin does not do is the point:

Pins fix geometry, never authorisation. A pinned request uses the pinned segments_version for tiles, columns and permutation, but composes M_auth against the current overlay — deny entries apply the moment they are accepted, pinned or not.

The consequence is visible to users and is not a bug: “a pinned drill-down can return fewer items than the viewport before it — is correct behaviour.” The composition stays coherent under mixed versions because M_auth is computed entirely in entity space, with the fragment's own watermark defining the live set; projection through the pinned permutation then drops row-absent entities via the sentinel, so there is no gap and no double count. For the same reason, fragments are built on a cache miss from the current generation's postings view and never from a pinned one: a fragment is authorisation state.

The three retirement rules

A deny entry cannot stay in the overlay forever; the overlay would grow without bound. So each entry needs a condition under which it may be dropped — a retirement rule. The design's recorded decision reads:

Three retirement rules, not one (amended r2): deletion denies by the epoch ledger with an insertion floor; suppressions only by unsuppress; evaluate entries at their compaction fold. r1's single rule was fail-open for two of the three.

Deletion denies retire by the epoch ledger. A deletion stamps its deny entry with a tombstone epoch d and applies a delta-tier tombstone at d immediately. The entry may leave the overlay only when no servable fragment epoch predates d. The fragment cache maintains a count of live fragments per postings epoch, whose lowest key is the minimum live epoch, and the lifecycle thread retires the retirable prefix below it after evictions and periodically. The cache additionally tracks a retirement floor — the highest epoch of any retired overlay entry, whether a deletion's d or an evaluate entry's fold epoch f — and refuses to insert any fragment whose epoch is below that floor. Without the floor, a pinned or slow request could rebuild an old-epoch fragment after the entries predating it were retired, and resurrect a deleted item or a revoked term. Refusal is cheap: the builder retries against current postings. The ledger is per worker and in memory, and losing it on restart is safe by construction, because the cache restarts cold.

Suppressions retire only on unsuppress, and never touch postings. The rule leaves no room for interpretation: a suppression is “never — suppression does not touch postings” retired by any epoch, and leaves “only by unsuppress. Non-retirable while active, by construction: no fragment rebuild ever excludes a suppressed entity, so its invisibility rests on the overlay entry for as long as the suppression stands.” Unsuppress removes the entry and publishes a side-manifest immediately, as all deny-state changes do. The obvious objection — that the active-suppression set then grows monotonically — is answered by treating its size as a metric: a growing suppression set is a policy signal, not a leak.

Predicate-change entries retire at their compaction fold. An evaluate entry carries the entity's current term set inline, and retires “not until compaction folds it — deltas cover newly flushed entities only, so a change to an existing entity's terms is invisible to postings in both directions.” Compaction rewrites the affected entities' postings from the term sets carried in their evaluate entries; after the fold the entry carries its fold epoch f and retires under the ledger rule above, with f participating in the retirement floor exactly as a deletion's d does. That symmetry is required, not decorative: a fragment predating the fold misreads the entity in both directions — a revoked term still present is fail-open, a granted term absent is merely wrong counts — so a floor raised only on deletion retirements “passes the deletion test and still fails open through a pre-fold fragment.” Before any fold, evaluate entries are immortal, which is why overlay growth under predicate churn schedules a compaction rather than just a fragment refresh.

An earlier revision had a single rule, and it was a rule about denies: every deny was assigned a retirement epoch. Evaluate entries are not denies, and the rule that governs them arrived only with the amendment quoted above — which is why the recorded verdict is that the single rule was fail-open for two of the three. For deletions it is right, because a deletion leaves a tombstone in the postings, so once every servable fragment postdates it the postings themselves carry the denial and the overlay entry is redundant. For suppressions it is fail-open. A suppression carries no postings-side signal at all — no tombstone, no fold — from which its invisibility can be re-derived, so an epoch-based timer expiring the entry resurrects the suppressed item with no unsuppress having occurred: any epoch eventually retires the entry and re-exposes the item. The third failure is the one the amendment had to generalise for: raising the floor only on deletion retirements leaves a pre-fold fragment insertable after an evaluate entry logically retires. Splitting the rules by disposition is the fix. Stated generally, the row that must never exist is “any path that loses or re-exposes an acked deny”; the ack ordering, the suppression rule, the insertion floor and the post-snapshot tombstone carry-forward each close one such path found in review, and all four carry conformance tests.
