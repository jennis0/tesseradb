Part II

The shape of the data

Two ideas carry the rest of this paper. An item is numbered twice, in two coordinate systems, for two different reasons; and the cost of what the service does is governed not by how many items are involved but by how they are laid out. Neither is novel alone. What is load-bearing is building the whole system on both at once.

4. Two coordinate systems

Every item has two questions asked of it, constantly and independently. May this viewer see it? And where does it sit on the map? The two want incompatible numbering schemes, and serving both from one numbering is how this kind of system usually goes wrong.

Permission data wants a permanent name. A grant, a suppression, a compartment membership, a deletion deny — each must survive rebuilds and compaction and mean the same thing in every temporal slice of the corpus. So every item gets a permanent entity ID: stable across temporal slices and rebuilds, never reused, never exposed outside the trust boundary. Every permission fact in the system is expressed in this space and nowhere else. Allocation is in append-only batches, so the numbering only grows at the end; with deletions in the mix the gap between the highest entity ID and the number of items that exist widens over time, which is a genuine long-term exhaustion concern.

Geometry wants the opposite: a numbering that reflects where an item is, so that items near each other on screen are near each other in the numbering. But position is not stable — a slice holding different items has a different spatial ordering — so a numbering derived from geometry would change out from under every permission fact ever recorded. Geometry therefore gets its own space. Each temporal slice separately assigns row IDs by spatial rank, and those row IDs are the array indices of the stored columns.

An explicit permutation relates the two. A slice stores a u32 array mapping entity ID to row ID, sized by the maximum live entity ID rather than by item count, with a sentinel for entities not present in that slice. The inverse is not stored separately: it is the entity-ID column of the row-ordered store, which is already there.

That independence is the point of the factoring, and it pays twice.

It pays first in storage. Because the term index is expressed in entity space, it is not duplicated per slice: within a partition there is exactly one index, shared across every slice, and a mask fragment is built once there and permuted into a particular slice's row space on demand.

It pays second, and more sharply, in compression. Row space is fixed by geometry; entity space is free within each append-only batch, because the order in which a batch is numbered is arbitrary — and an arbitrary choice is a resource. Tessera spends it by assigning entity IDs within a batch sorted by term signature, so items sharing the same set of access terms end up adjacent. Term postings then form long runs inside each batch's ID range, and head terms encode as run containers. In the design's own words, "it costs nothing, does not weaken I9, and is safe only because of I10" — safe only because entity IDs never cross the trust boundary, so an ordering that encodes something about an item's permissions cannot be observed by a client.

The measured gains are large and the counterfactual is flat. Arrival-order allocation gives mean posting run lengths of 1.00–1.26 against a random baseline of 1.000 — nothing at all. Signature sorting, simulated against the Phase 0 corpus, moves posting storage by 8.9× on category-shaped labels and 36.7× on the synthetic hash policy, a cached session fragment by between 6× and 1,614×, and mask union cost at equal coverage by up to 130×. Because entity-ID assignment is permanent by invariant, none of this can be retrofitted: arrival-order allocation would lock in an uncompressed index until a full re-allocation rebuild, which is why the signature-sorted allocator is in the walking skeleton rather than on a later optimisation list.

The factoring has a price that constrains the whole serving design. Permuting a mask from entity space into row space is expensive: 8.8 s for a 69M-item mask at 109. That is fine once per session and fatal per viewport, so the permuted mask is cached per token, slice and pin — if that step ever drifts onto the per-viewport path, the system dies. Even the construction matters: naive iterate-and-insert is slow because the inserts arrive out of order, so the implementation gathers entity_to_row[e] into a flat buffer, radix sorts it, and bulk-constructs.

5. Morton ranking

Row IDs are assigned by spatial rank, and the ranking function is chosen for one specific algebraic property rather than for locality in general.

Coordinates are first quantised onto a 216 × 216 integer grid. The bits of the two coordinates are then interleaved to produce a single Morton code, also called a Z-order code; items are sorted by that code and each item's row ID is its rank in that order. Within a leaf tile the ordering is by display priority rather than by deeper Morton bits, which is what makes level-of-detail sampling cheap later.

The interleaving is worth doing by hand once. Take a 4 × 4 grid, so each coordinate is two bits. Write x as x₁x₀ and y as y₁y₀, and interleave them most-significant first as y₁ x₁ y₀ x₀. The cell at x = 2, y = 1 has x = 10 and y = 01, so its code is 0 1 1 0 — decimal 6. Doing that for all sixteen cells gives:

x = 0x = 1x = 2x = 3
y = 00145
y = 12367
y = 2891213
y = 310111415

Read off the four quadrants. The top-left 2 × 2 block holds codes 0–3, the top-right 4–7, the bottom-left 8–11, the bottom-right 12–15. Each quadrant is a block of four consecutive integers, and the leading pair of bits names which quadrant it is. That generalises: each successive pair of bits identifies a quadrant one level further down, so a quadtree tile at any depth is exactly the set of codes sharing a given prefix — one contiguous range of codes, and therefore, since row IDs are the rank in code order, one contiguous range of row IDs. This is the prefix property, and it is why Morton is chosen over Hilbert: Hilbert has better locality, but only Morton has the prefix property, and that single property underpins tile queries, density counts, level-of-detail sampling and sharding alike. A precomputed tile table maps prefixes to rank ranges, so answering "which row IDs are in this tile" is two lookups and no search.

Note the division of labour. A tile's identity is purely geometric — a Morton prefix — while its rank range is per-partition and per-slice. That is what lets independently ranked partitions agree on what a tile is without agreeing on any row ID.

Two qualifications belong here, because the prefix property is easy to over-sell. The first is that a viewport is not a tile: an arbitrary rectangle on screen is covered by a set of tiles, and a single logical tile can itself correspond to several ranges once a partition holds multiple segments, so the interface between the query layer and the store is deliberately typed as tile → set of ranges.

The second is more consequential. Morton ordering makes tiles contiguous; it does not make permission masks contiguous. Phase 0 measured this, comparing the mean run length of a mask in row order against the run length expected of a random mask of the same density. A deliberately structureless control policy returns exactly 1.00, validating the estimator; the most realistic principal shape available sits at 1.03–1.15; category-derived policies reach only 2.32, and the most clustered case measured reaches 5.11 — and those category-derived families are the ones the topic-correlation caveat says are flattered, by up to roughly 5×, so they are upper bounds. The recorded conclusion is blunt: realistic masks are essentially scattered, Morton order buys no compression for any family, and the entity- and row-space serialisations of a mask are within noise of each other. The uniform-scatter assumption the earlier scaling analysis had flagged as its weakest premise turned out to be approximately true. There is no hidden upside — which is why compression is bought in entity space, by the signature-sorted allocation of chapter 4, and nowhere else.

One sizing note. At 109 items the 216 × 216 grid gives 0.23 points per cell, so quantisation collisions are not a constraint; past roughly 4 × 109 the grid must widen and the codes become 64-bit.

6. Roaring, and the cost model

The last structural idea is how the sets themselves are represented. A viewer's visible set, a term's postings, a filter's result are all sets of integers over a bounded universe, and all are stored as Roaring bitmaps: the universe is split into blocks of 216 consecutive integers, and each block is independently encoded as a sorted 16-bit array, a literal bit array, or a list of run-length pairs, whichever is smallest for that block's contents. Those blocks are called containers, and the choice of encoding is per container, not per bitmap.

The per-container choice is what makes a wildly skewed term distribution harmless. A head term whose postings are dense and contiguous becomes run containers; the long tail of rare terms becomes small sorted arrays. The crossover between a sorted array and a literal bit array follows from arithmetic rather than tuning: a bit array for a block is a fixed 8 KB whatever it holds, while a sorted array costs two bytes per member, so the array stops being smaller once the block holds more than a few thousand members. The precise threshold is a property of the Roaring format and its reference implementation rather than of this system — see Chambi, Lemire, Kaser and Godin, "Better bitmap performance with Roaring bitmaps" and the CRoaring implementation — and Tessera inherits it. Below container scale entirely, terms with fewer than a few hundred members are held as plain sorted 32-bit arrays; at the measured vocabulary of 117 million terms, 34.4% are singletons.

Now the headline, which is the single sentence the rest of the design is written against:

Bitmap operations cost O(containers touched), not O(cardinality).

The consequences are not subtle. A term with 100,000 postings spans about 15,259 containers when its members are scattered across a 109 universe — that is every container in the universe, since 109 ÷ 216 is 15,259 — and about 2 containers when they are contiguous. Identical cardinality, roughly 7,500× difference in merge work. Measured at 109, building a viewer's mask at 25% coverage costs either 21.7 ms or 2,885 ms for the same 125.12 MB serialised mask, depending on nothing but posting shape.

The same model explains why the scaling curves are flat. Union cost is linear in containers spanned, and the per-container constant drifts up only about 2× across 400× of scale — 54 ns at 2.42M items, 95 ns at 250M, 114 ns at 109 — which is the memory hierarchy, not the algorithm. Two regimes exist, with constants 13× apart: 114 ns per container where postings are sparse and containers are arrays, against 1.54 µs where they are dense and containers are 8 KB bit arrays. Hence the mask-building kernel needs two algorithms, choosing on container density between an n-way Roaring union and a concatenate-radix-sort-and-bulk-construct pass. Hence, too, vocabulary size is almost free on the authorisation path: mask build barely moves between 10 million and 117 million distinct terms, because union cost depends on the postings granted, not the size of the dictionary. The realistic worst case measured — 104 grants over category-shaped labels — is 588 ms.

Now the consequence that matters for a map. Once a viewer's mask is materialised, answering a viewport is a set of range-cardinality queries over it, and their cost is governed by how many containers the ranges touch. The mask has roughly 15,000 containers in total, so any set of ranges is bounded above by a single traversal of it. Measured at 109 items against real Morton tiles:

Counting is flat at 0.1–0.3 ms across every zoom level, including depth 0, where a single call counts the entire billion rows in 191 µs. A billion-row viewport is not meaningfully more expensive than an eight-thousand-row one, because both are bounded by the same traversal of the same ~15,000 containers. Cost scales with the containers a viewport's ranges touch — with screen area and mask structure — and not with the size of the corpus behind it. That is the scale answer, and every subsequent decision in this paper is written against it: the on-disk layout, the query path, the sharding, and which aggregates the service is willing to offer at all.

Which brings the necessary limit. This is a counting engine, not an aggregation engine. Counts, densities, existence, membership and samples are O(containers) and effectively free regardless of how many items are involved. Sums, means and percentiles are O(visible items), because the values must be gathered, and no bitmap construction recovers this: per-term partial sums double-count, since an item carries several terms and terms do not partition the corpus. A masked global mean over 108 visible items is a scan, and saying so plainly is better engineering than pretending otherwise. A smaller asymmetry sits in the same family: rank and select over a Roaring bitmap are not constant-time — both cost O(blocks before the position) — so per-tile selections are batched from a computed base rank.

Every figure quoted here comes from the Phase 0 measurements: synthetic access-control policies over a real corpus of 2.42 million arXiv papers, scaled to 109 points, on WSL2 with 12 cores, 39 GB and an RTX 3080 — an environment chosen for memory-mapping and page-cache fidelity rather than latency. The timings are indicative rather than certified; the ratios between them are the durable part.
