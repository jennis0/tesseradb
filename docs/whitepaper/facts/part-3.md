# Part 3 facts — plugin boundary, DNF/terms, mask construction, signature-sorted IDs, request path, vocabulary

## The authorisation plugin boundary — what crosses it and what does not

- The core knows only that an item carries a set of opaque term IDs, a token carries a set of satisfied term IDs, and an item is visible iff those sets intersect; everything about how terms are derived sits behind two caller-supplied functions — source: .ignore/tessera-architecture-design.md §6.1
- The authorisation schema is out of scope for the service: the service never receives a modelling hyperparameter or policy semantics, only opaque terms — source: .ignore/tessera-architecture-design.md §2.1
- `terms_of_label(item_label) -> {term descriptor}` runs once per item at ingest and must be fast — source: .ignore/tessera-architecture-design.md §6.1
- `terms_of_auth(auth_data) -> {term descriptor}` runs once per authorisation and may be expensive — source: .ignore/tessera-architecture-design.md §6.1
- The term index, mask construction's union, label containment, level of detail, filters, partitioning and storage never know where terms came from, only the derivation did — source: .ignore/tessera-architecture-design.md §6.1
- Four contract obligations on the plugin author beyond I5's consistency requirement: canonical descriptors, determinism, declared cardinality bounds, and cost asymmetry (data function runs per item at ingest, auth function runs per authorisation) — source: .ignore/tessera-architecture-design.md §6.1
- Both functions emit opaque byte strings; the service interns them to IDs in a shared, append-only namespace, so agreement between the two functions is byte-equality of canonical descriptors — source: .ignore/tessera-architecture-design.md §6.1
- Declared cardinality bounds (distinct terms, terms per item, satisfied terms per token) are sizing declarations, not enforcement triggers — exceeding one warns and never excludes — source: .ignore/tessera-architecture-design.md §6.1
- An auth-function change invalidates masks (its version joins the mask cache key); a data-function change alters item→terms and requires a full reindex (its version belongs in segment metadata) — source: .ignore/tessera-architecture-design.md §6.1
- A plugin may accept a signed, principal-bound assertion (JWS, SAML assertion, attribute certificate) and verify it against trust anchors embedded in the plugin itself; signature verification is pure computation so it stays compatible with the determinism obligation — source: .ignore/tessera-architecture-design.md §6.1
- Expiry cannot be checked inside a deterministic plugin (no clock); the plugin surfaces the credential's `not_after` and the host enforces it and clamps token lifetime — source: .ignore/tessera-architecture-design.md §6.1
- There is no online revocation: I6 and the capability-free execution environment forbid credential lookups by construction, so revocation is bounded by assertion lifetime — source: .ignore/tessera-architecture-design.md §6.1
- The auth and data functions may ship as separate wasm modules (config: `plugin.data`, `plugin.auth`), keeping the two blast radii operationally separate — rotating trust anchors changes only the auth hash (mask-cache invalidation), never `data_plugin_hash` (a full-reindex event) — source: .ignore/tessera-contracts-spec.md §4.1
- Plugin ABI: wasm32, no WASI imports (instantiation refuses any); exports `alloc(len: u32) -> u32` and `dealloc(ptr: u32, len: u32)`; variable-length values cross as packed `u64` = `ptr << 32 | len` — source: .ignore/tessera-contracts-spec.md §4.2
- Host allocates inputs via `alloc`, calls the export, copies the output, then calls `dealloc` on both input and output buffers; a module's output must stay valid until that `dealloc`, and no buffer outlives its call — source: .ignore/tessera-contracts-spec.md §4.2
- Plugin ABI exports table: `abi_version` `() -> u32` must return 1; `declared_bounds` `() -> u64` returns `{max_distinct_terms, max_terms_per_item, max_terms_per_token}`; `terms_of_label` `(u64) -> u64` returns `{"terms": ["<hex descriptor>", …]}`; `terms_of_auth` `(u64) -> u64` returns `{"terms": [...], "not_after"?: unix_seconds}` — source: .ignore/tessera-contracts-spec.md §4.3
- An empty `terms` list is valid: default deny (label side), zero-visibility token (auth side); a trap or structurally malformed JSON fails the operation closed (`500 fail-closed`); exceeding a declared bound warns and proceeds — source: .ignore/tessera-contracts-spec.md §4.3
- Determinism is environmental (no clock, no WASI); `not_after` is enforced by the host clock; batching is an additive `abi_version = 2` candidate with no current customer — source: .ignore/tessera-contracts-spec.md §4.3
- Prior art: partial evaluation compiles a policy into a residual filter in disjunctive normal form, which is precisely the auth function's job — so driving authorisation from a policy engine later is a matter of writing one plugin, not a redesign — source: .ignore/tessera-architecture-design.md §6.1

## Grants as boolean expression, DNF normalisation, terms, term index, postings and union

- A term is opaque; whether the reference model is used is Appendix E, one implementation of the two functions — source: .ignore/tessera-architecture-design.md §2.1
- Under the reference plugin, categories are drawn from five dimensions (one conjunctive dimension of 0–5 categories per item, three small disjunctive dimensions, one disjunctive dimension of vocabulary 10⁵–10⁶ categories); a unit is a conjunction of five clauses; an item's predicate is an arbitrary monotone nesting of AND and OR over units, and normalising to disjunctive normal form yields the terms the core indexes — each a single unit or an interned conjunction of units — source: .ignore/tessera-architecture-design.md Appendix E
- Item predicates are written as access expressions in the `accumulo-access` grammar: tokens combined with `&` and `|`, parentheses for grouping, no negation, no mixing of `&`/`|` at one level without parentheses — absent negation the predicate is monotone so DNF normalisation terminates and the term index is sound — source: .ignore/tessera-architecture-design.md Appendix E
- Consistency (I5) reduces to one rule in the reference implementation: an item is indexed under its DNF terms and nothing finer; a disjunct that is a conjunction of units must be interned as a term in its own right, and the item must not appear in the postings of its constituent units — source: .ignore/tessera-architecture-design.md Appendix E
- The risk this implementation carries is measured, not theoretical: published work on boolean expression indexing found DNF normalisation infeasible beyond nesting depth 2 for comparable workloads — the mitigation is plugin-side minting of synthetic terms for deep subexpressions, keeping terms per item linear in expression size at any nesting depth — source: .ignore/tessera-architecture-design.md §16 / Appendix E
- DNF expansion was not measured in Phase 0 "because here it cannot be" — the project's own predicates are its own knob, so measuring their expansion measures the knob; both ends of the minting conservation law were measured instead: auth-side (satisfied terms per token) swept to w=10⁴, item-side (terms per item) to 1000 via `hiterms` — source: probes/results.md §1
- The term index maps each term to a Roaring bitmap of entity IDs; Roaring's per-block encoding makes the skewed size distribution harmless: head terms become run containers, the long tail small sorted arrays; store terms below a few hundred members as plain sorted int32 arrays — source: .ignore/tessera-architecture-design.md §6.2
- Bounds warn, they never exclude: exclusion was dropped (r16, measured) because a predicate is a monotone disjunction so more terms means broader intended visibility, and exclusion answered "visible to many" with "visible to none"; measurement found no change in the shape of authorise-path cost at ~130 terms per item, "no invariant depends on terms-per-item" — source: .ignore/tessera-architecture-design.md §6.2
- Mask construction is performed once per distinct auth input, at authorisation; the auth function yields satisfied term descriptors, the service resolves them to IDs and unions the corresponding postings, per partition the token can reach — source: .ignore/tessera-architecture-design.md §6.3
- The postings are built from a pre-exploded `(entity_id, term_id)` pair relation, joined as a semi-join — this is a requirement, not an optimisation: the natural alternative (terms as a list column, test containment against the presented set) is "roughly three orders of magnitude slower in every implementation measured" because containment operators rebuild a probe structure per row — source: .ignore/tessera-architecture-design.md §6.3
- Measured: the pair-relation semi-join is reassigned away from the authorise path — "36 ms at 2.42M for w=10⁴, but 3.9–10.3 s at a tiled 249.5M corpus" (tripping the plan's own multi-second criterion at scale), while postings union is "4–540× faster, 36–530 ms at 249.5M" — source: probes/results.md §4.1
- At the true 10⁹, postings-union path (min of 3, real vocabulary structure): categories-subclass head 25% coverage, w=9, |mask|=264.3M, union **"230.6"** ms, ser 125.12 MB; categories-subclass random w=10,000, coverage 41.6%, |mask|=416.1M, union **"588.0"** ms; hash-flat head 25%, w=2,301, union **"2,885.0"** ms; hash-flat random w=10,000 (100% coverage, degenerate), union **"13,783.5"** ms — source: probes/results.md §4.2
- "The realistic worst case — 10⁴ grants over category-like labels — is **588 ms**, inside the 0.14–2 s band projected from 250M" — source: probes/results.md §4.2
- "Entity-space contiguity is worth up to ~130×, at identical coverage and identical mask size" — union cost is Σ over granted terms of containers spanned, not mask cardinality; hash-flat's terms span "~15,259 containers (all of them) at ~6.5 postings per container" versus categories-archive's "~37 densely-filled containers, 400× fewer visits" — source: probes/results.md §4.2
- Union cost is linear in containers spanned, with per-container cost drifting up only ~2× across 400× of scale; at fixed ~1% coverage: scale 250,000 → 399 containers, 0.0 ms; scale 2,422,486 → 3,693 containers, 0.2 ms, 54 ns/container; scale 250,000,000 → 380,868 containers, 36.3 ms, 95 ns/container; scale 1,000,000,000 → 1,523,216 containers, 173.6 ms, 114 ns/container — source: probes/results.md §4.3b
- Per-container constant differs by 13× between regimes: categories-subclass at 10⁹ head 25% is 125,279 containers, 193.1 ms = "1.54 µs/container" (dense bitmap containers), against hash-flat's "114 ns" (sparse array containers) — source: probes/results.md §4.3b
- Dictionary scale is a storage problem, not an authorise-path problem: mask build "barely moves between 10M and 117M terms" because union cost depends on granted postings, not vocabulary size — source: probes/results.md §4.3
- The kernel needs two algorithms: Roaring n-way union costs O(terms × containers spanned); concatenating sorted posting arrays, radix sorting and bulk-constructing costs O(total postings) and wins in the sparse-array regime, Roaring union wins in the dense-bitmap regime — source: probes/optimisations.md §1.2

## Mask construction: built once per authorisation, reused per session

- The two-stage split: "Authorise" accepts the caller's authoritative auth data, resolves it to satisfied terms, performs mask construction, and returns an opaque token — "Paid once per distinct auth input"; "Retrieve" accepts a token plus a query and returns the rendered payload, "Single-digit milliseconds, called many times per second while a user pans" — source: .ignore/tessera-architecture-design.md §2.2
- "Every retrieval is cheap, because it operates against a precomputed mask rather than re-deriving authorisation" — source: .ignore/tessera-architecture-design.md §2.2
- Masks are content-addressed (tokens are not): the canonical key is a hash of the satisfied term set together with the authorisation plugin's version and the identity of the postings the mask was built from (the bundle's manifest digest) — a hash of the raw auth data is a fast path in front of it — source: .ignore/tessera-architecture-design.md §2.3
- Eviction is transparent: the auth data is retained alongside the mask so that if a mask is evicted under memory pressure, retrieval rebuilds it rather than failing at an arbitrary moment — source: .ignore/tessera-architecture-design.md §2.3
- Cache table: token mask fragment (pre-composition), entity space, keyed on (auth-data hash, auth-plugin version, partition), invalidated by "nothing — content-addressed" — source: .ignore/tessera-architecture-design.md §8.5
- Expected latency, warm: "low single-digit milliseconds per viewport with a single segment" — source: .ignore/tessera-architecture-design.md §10.4
- Measurement condition for all Phase 0 timings: environment "WSL2, 12 cores, 39 GB, RTX 3080"; "Timings are indicative, not certified... Treat ratios as evidence and absolutes as a starting point" — source: probes/results.md (header)

## Signature-sorted entity ID assignment: measured compression, and I9 permanence

- I9 verbatim: "**I9 — Entity IDs are append-only and never reused.** Masks and generating sets are sets of entity IDs held in caches with non-zero lifetime; reissuing a deleted item's ID grants the new item every access the old one had." — source: .ignore/tessera-architecture-design.md §4
- I10 verbatim: "**I10 — Entity IDs never cross the trust boundary.** They are dense and assigned in ingest order, so the gap between two visible IDs is a count of unauthorised items ingested in the same window. Clients receive per-session opaque handles instead. This is also what makes the ingest-order optimisation in §11.1 safe (C6)." — source: .ignore/tessera-architecture-design.md §4
- Entity IDs are allocated in append-only batches; the order within a batch is a free choice, and §11.1 spends it deliberately — source: .ignore/tessera-architecture-design.md §5.1
- "Spend the entity-ID ordering on posting compression": assign entity IDs within a batch sorted by term signature so term postings form long runs inside each batch's ID range; "It costs nothing, does not weaken I9, and is safe only because of I10" — source: .ignore/tessera-architecture-design.md §11.1
- Entity IDs must not be assigned in Morton order (the tempting alternative), because that would give permission-space IDs spatial meaning, turning the ID gap between two visible points into an estimate of unauthorised data nearby (C6) — source: .ignore/tessera-architecture-design.md §11.1
- "**Measured (r18):** created-order assignment yields run lengths of 1.00–1.26 against a 1.000 random baseline — nothing — while signature-sorted assignment buys 8.9–36.7× on posting storage and up to 130× on union cost at equal coverage" — source: .ignore/tessera-architecture-design.md §11.1
- "The compression comes entirely from this ordering, and because I9 makes assignment permanent it ships in the Phase 1 allocator or not at all." — source: .ignore/tessera-architecture-design.md §11.1
- Signature-sorted entity assignment, simulated as a global re-permutation: categories-subclass postings total "7.7 → 0.9 MB (**8.9×**)", 25% fragment "303 → 47 KB (**6×**)"; surnames postings total "44.8 → 45.5 MB (1.0×)" (no gain), 25% fragment "303 → 303 KB (1×)"; hash t=100 postings total "552.9 → 15.1 MB (**36.7×**)", 25% fragment "303 KB → **0.2 KB** (**1,614×**)" — source: probes/results.md §4.4
- These figures are "floors on the scale effect": at 2.4M the mean categories group is 44 entities so runs are short, at 10⁹ groups are ~400× longer and index size converges on O(Σ|signature| × batches) — a function of policy complexity, not corpus size — source: probes/results.md §4.4
- "Nothing runs under created-order entity IDs (1.00–1.26 against a 1.000 random baseline). §11.1's posting compression has to come from signature-sorted assignment within batches, not from arrival order." — source: probes/results.md §2
- Optimisations doc classification: "Signature-sorted entity allocation, in the Phase 1 allocator — **DECIDED** *(serving + session memory)*"; table of gains: posting storage 8.9× (categories) to 36.7× (t=100), cached session fragment 6× to 1,614×, mask union at equal coverage up to 130× — source: probes/optimisations.md §2.1
- "This must be in the Phase 1 allocator, not added later. I9 makes entity-ID assignment permanent, so shipping created-order in the walking skeleton locks in an uncompressed index until a full re-allocation rebuild." — source: probes/optimisations.md §2.1
- Only optimisations that change the shape of the postings the mask build reads touch serving; entity ordering is named as one that does — source: probes/optimisations.md (front matter)
- Row-space (Morton) mask stays scattered regardless of entity-space ordering: "Entity space only; the row-space mask stays scattered (§5)." — source: probes/results.md §4.4
- Container footprint, not cardinality, is the cost model for every bitmap operation measured; it explains the 130× union spread and the 8.9–36.7× posting compression from signature ordering — source: probes/optimisations.md §0
- Two mechanisms account for most of what was measured: container footprint as cost model, and "Almost every headline is policy-dependent" — signature alignment, posting compression and union speed depend on label shape, not corpus size — source: probes/results.md §8

## The end-to-end request path (§2.6), step by step

- **Once per session — authorise:**
  1. Hash the presented auth data; look up (auth-data hash, auth-plugin version) in the mask cache; on a hit, return a token — source: .ignore/tessera-architecture-design.md §2.6 step 1
  2. On a miss, `terms_of_auth(auth_data)` yields term descriptors; the service interns them to term IDs — source: .ignore/tessera-architecture-design.md §2.6 step 2
  3. Compute the reachable partition set: a partition is reachable only if the token satisfies every term in its required set (intersection of compartment markers across all disjuncts); unreachable partitions are never contacted (I13) — source: .ignore/tessera-architecture-design.md §2.6 step 3
  4. Per reachable partition, union the postings of the satisfied terms into `M_token`, a Roaring bitmap in entity space (I4); postings are built from the exploded (entity_id, term_id) relation by semi-join — source: .ignore/tessera-architecture-design.md §2.6 step 4
  5. Write frozen-format, cache alongside the auth data so eviction rebuilds rather than fails, and return an opaque token — source: .ignore/tessera-architecture-design.md §2.6 step 5
- **Per viewport — retrieve:**
  1. Pin once: resolve the segment-set version and use it for the tile table, columns, permutation and candidate lists alike (I11); the mask fragment carries its own watermark — source: .ignore/tessera-architecture-design.md §2.6 step 1 (retrieve)
  2. Compose the effective mask: `M_auth = (M_token \ L) ∪ direct_eval(L)`, where L is the overlay unioned with every entity at or above the watermark (I1); loaded through `frozen_view` over the mmap — no deserialisation, no allocation — source: .ignore/tessera-architecture-design.md §2.6 step 2
  3. Apply filters to obtain `M_sel = M_auth ∧ filters`; filters are order-independent set producers composed by intersection and never touch authorisation (I12) — source: .ignore/tessera-architecture-design.md §2.6 step 3
  4. Project into row space: iterate the mask in order, gather `entity_to_row[e]` into a flat buffer, radix sort, bulk-construct; cache per (token, slice, pin) — "the only point at which the two ID spaces meet" — source: .ignore/tessera-architecture-design.md §2.6 step 4
  5. Decompose the viewport into a few hundred quadtree tiles at the target depth, each a contiguous [lo, hi) row range by the Morton prefix property — source: .ignore/tessera-architecture-design.md §2.6 step 5
  6. Count per tile: `intersect_with_range` culls empty tiles, `range_cardinality` gives the exact masked count with no data file touched — cost in containers, not rows — source: .ignore/tessera-architecture-design.md §2.6 step 6
  7. Select per tile: at or below k take everything; above k take the k lowest-priority visible items, evaluated directly from the mask where coverage is low or through the node's precomputed candidate list where it is high, crossing at a few percent, the choice decidable from the count in step 6; priority is a hash-derived per-point constant and mask-independent (I7) — source: .ignore/tessera-architecture-design.md §2.6 step 7
  8. Collect the selected row IDs into one u32 array; Morton-order processing leaves it already sorted, so the gather is forward-sequential-with-gaps and cooperates with readahead — source: .ignore/tessera-architecture-design.md §2.6 step 8
  9. Gather through tight loops over the mmap'd Arrow columns, writing directly into the output Arrow arrays — source: .ignore/tessera-architecture-design.md §2.6 step 9
  10. Translate out: row IDs to entity IDs to per-session opaque handles; entity IDs never cross the boundary (I10) — source: .ignore/tessera-architecture-design.md §2.6 step 10
  11. Serve labels separately, gated on `M_auth` and never on `M_sel`, so filtering narrows the points without dissolving the map; evaluated per request, nothing cached above the check (I3) — source: .ignore/tessera-architecture-design.md §2.6 step 11
- "Three properties carry the design": steps 6–7 give exact counts and post-mask sampling both from bitmap arithmetic over contiguous ranges so cost scales with screen area not corpus size; step 4 is the sole meeting point of the two ID spaces, making I4 a type rule rather than a convention; nothing between steps 2 and 10 reads a column except through a masked row-ID set, which is I2 in structural form — source: .ignore/tessera-architecture-design.md §2.6

## Invariants I2, I7, I9, I10 verbatim

- "**I2 — Derived quantities are functions of visible data only.** Any aggregate shown — centroid, hull, count, density, label — must be computable from the items inside `M_auth` alone. A quantity derived from the full dataset and merely *gated* on a threshold is a disclosure, not a filtered view. Exceptions are enumerated in Appendix C; an exception not in that table is a bug. Enforced by construction rather than by discipline: the mask is the only entry point to the geometry arrays (§10.4), so there is no path along which an aggregate over unmasked rows can be built." — source: .ignore/tessera-architecture-design.md §4
- "**I7 — Sampling happens after masking, never before.** The sample of an authorised set is not the authorised portion of a global sample. Any level-of-detail step must be *defined* over the visible set; precomputed unmasked structures may be used only as a fast path with an exact fallback (§7.2)." — source: .ignore/tessera-architecture-design.md §4
- "**I9 — Entity IDs are append-only and never reused.** Masks and generating sets are sets of entity IDs held in caches with non-zero lifetime; reissuing a deleted item's ID grants the new item every access the old one had." — source: .ignore/tessera-architecture-design.md §4
- "**I10 — Entity IDs never cross the trust boundary.** They are dense and assigned in ingest order, so the gap between two visible IDs is a count of unauthorised items ingested in the same window. Clients receive per-session opaque handles instead. This is also what makes the ingest-order optimisation in §11.1 safe (C6)." — source: .ignore/tessera-architecture-design.md §4
