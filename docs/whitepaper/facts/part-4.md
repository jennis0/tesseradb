# Part 4 facts: LOD, sampling, fallback ladder, label gating, two-mask model, compartmented partitions

## Invariants (verbatim)

- I2 — verbatim: "Derived quantities are functions of visible data only. Any aggregate shown — centroid, hull, count, density, label — must be computable from the items inside `M_auth` alone. A quantity derived from the full dataset and merely *gated* on a threshold is a disclosure, not a filtered view. Exceptions are enumerated in Appendix C; an exception not in that table is a bug. Enforced by construction rather than by discipline: the mask is the only entry point to the geometry arrays (§10.4), so there is no path along which an aggregate over unmasked rows can be built." — source: .ignore/tessera-architecture-design.md §4
- I3 — verbatim: "Labels are served iff their generating set is a subset of `M_auth`. Never of the filtered selection mask (§8.1). Evaluated per request, with nothing caching a label decision above the check (§7.6)." — source: .ignore/tessera-architecture-design.md §4
- I7 — verbatim: "Sampling happens after masking, never before. The sample of an authorised set is not the authorised portion of a global sample. Any level-of-detail step must be *defined* over the visible set; precomputed unmasked structures may be used only as a fast path with an exact fallback (§7.2)." — source: .ignore/tessera-architecture-design.md §4
- I12 — verbatim: "Filters narrow rendering; they never touch authorisation. A filter may reduce which authorised items are drawn. It may never enlarge the authorised set, relax a label's containment test, or permit the cluster frontier to descend below the depth `M_auth` alone would allow. Operationally: **a filter may move the frontier up, never down** (§8.4)." — source: .ignore/tessera-architecture-design.md §4
- I13 (for reference, governs cross-partition composition used throughout) — verbatim: "A partition not consulted fails closed. Where a query or a containment test spans partitions (§12), a partition the token cannot reach counts as contributing *nothing satisfied* — never as vacuously satisfied. The natural implementation, which checks only the partitions it queried, serves labels it should withhold." — source: .ignore/tessera-architecture-design.md §4

## Priority-based level of detail (§7.1–7.2)

- A viewport resolves to a small set of tiles, each a contiguous row-ID range within a segment, and the query is an intersection of the mask with those ranges — source: .ignore/tessera-architecture-design.md §7.1
- `range_cardinality` gives the exact count of visible items in any tile at any zoom without touching point data, so a full per-user density pyramid is a few thousand range-count calls and exact rather than estimated — source: .ignore/tessera-architecture-design.md §7.1
- With multiple live segments a tile resolves to one range per segment and counts sum — source: .ignore/tessera-architecture-design.md §7.1
- Global LOD sampling is incorrect under masking (I7): a principal authorised for a small or clustered slice would see a nearly empty screen while thousands of authorised items sat invisible beneath a sample that selected around them — source: .ignore/tessera-architecture-design.md §7.2
- Every item carries a fixed pseudo-random priority, derived by hashing its entity ID — source: .ignore/tessera-architecture-design.md §7.2
- A tile's sample is the k lowest-priority items in that tile inside the governing mask, where k is the on-screen mark budget per tile — source: .ignore/tessera-architecture-design.md §7.2
- Nothing in that definition references unmasked data, so it satisfies I7 by construction — source: .ignore/tessera-architecture-design.md §7.2
- It nests provably: an item among the k lowest-priority visible items in a parent tile is necessarily among the k lowest in whichever child contains it, because the child's visible set is a subset — source: .ignore/tessera-architecture-design.md §7.2
- An earlier design selected by rank position using a bit-reversal sequence, which does not nest across a change of population — a parent's pick at rank fraction ¼ lands at local rank 0 of its second child, which does not select its own rank 0 until far beyond any plausible k, so essentially every representative popped on zoom-in — source: .ignore/tessera-architecture-design.md §7.2
- Priority also composes across partitions where rank position would not (§12.3) — source: .ignore/tessera-architecture-design.md §7.2
- Step 6 of §2.6 already yields the tile's exact masked count before any selection happens, so choosing between the two evaluation strategies below costs nothing to make — source: .ignore/tessera-architecture-design.md §7.2
- Candidate lists: precompute, per tile node, the top c·k items by priority, unmasked, as row IDs; at query time filter by the mask and take the first k — source: .ignore/tessera-architecture-design.md §7.2
- A list of width c·k yields about c·k·coverage survivors, so it produces k of them only above coverage 1/c; at c=4 that is 25%, which given 10^4 grants against 10^5–10^6 categories describes very few principals — source: .ignore/tessera-architecture-design.md §7.2
- Widening helps linearly and costs linearly: 1% coverage needs c=100, which is comparable in size to the hot columns; treat the lists as an optimisation for high-coverage principals, not as the general path — source: .ignore/tessera-architecture-design.md §7.2
- Direct evaluation: take the visible row IDs in the tile's range straight from the mask via `range_uint32_array` (free), read their priorities, keep the k lowest; cost is bounded by the tile's priority block regardless of coverage, and it falls as coverage falls — source: .ignore/tessera-architecture-design.md §7.2
- The two approaches move in opposite directions and cross at a few percent coverage; descent multiplies work rather than dividing it — merging four children's lists yields four times the candidates, so reaching k survivors from d levels down visits the geometric sum of 4^d nodes: work proportional to 1/coverage, not to log(1/coverage) — source: .ignore/tessera-architecture-design.md §7.2
- Concretely, at c=4 and k=30 over 10^4-row tiles: about 21 nodes at 5% coverage against roughly 10 pages for direct evaluation, 85 nodes at 1%, and 5,461 nodes at 0.01% against a single page — source: .ignore/tessera-architecture-design.md §7.2
- Below roughly 5% coverage, evaluate directly; above it, use the list; both compute the same definition, so I7 holds either way — what changes is only which is cheaper — source: .ignore/tessera-architecture-design.md §7.2
- The measurement is now in (r18; probes, results §5): realistic masks are essentially scattered under Morton order, and at working coverages 12–99% of occupied depth-6 tiles fall below the ~5% crossover, and for tail-only principals essentially all do — source: .ignore/tessera-architecture-design.md §7.2
- Direct evaluation is the main selection route; candidate lists serve the dense cores of head principals; authorisation does not usefully correlate with position, so there is no hidden upside to wait for — source: .ignore/tessera-architecture-design.md §7.2
- Where a tile spans multiple segments, allocate k across segments in proportion to visible count — source: .ignore/tessera-architecture-design.md §7.2
- Priority sampling composes exactly across compartmented partitions: because priority is a global per-item property, the k lowest-priority visible items in a tile equal the k lowest of the union of each partition's k lowest — source: .ignore/tessera-architecture-design.md §12.3

## Consequence of getting the sampling order wrong (I7)

- "The sample of an authorised set is not the authorised portion of a global sample" — sampling before masking would let a small or clustered authorised slice appear as a nearly empty screen while thousands of authorised items sat invisible beneath a sample that selected around them — source: .ignore/tessera-architecture-design.md §7.2 (and I7, §4)

## Density (§7.3)

- Exact per-tile visible counts are free from §7.1, so use them: drive a density underlay from the count pyramid, or modulate mark alpha and k by count — source: .ignore/tessera-architecture-design.md §7.3
- Without this, a tile holding twelve visible items and one holding four million render identically — source: .ignore/tessera-architecture-design.md §7.3
- The counts are per-user and exact, so no disclosure beyond §7.1 — source: .ignore/tessera-architecture-design.md §7.3

## Drill-down (§7.4)

- The set behind a rendered representative is its tile's range intersected with the mask, already computed to place it; hovering yields the exact count; a detail panel is further selections over the same range — source: .ignore/tessera-architecture-design.md §7.4
- No adjacency structure is stored, because Morton ordering makes containment implicit in the row IDs — source: .ignore/tessera-architecture-design.md §7.4
- Where a tile is small enough to materialise, compute breakdowns exactly; above that, sample and say so — source: .ignore/tessera-architecture-design.md §7.4
- Do not precompute per-tile summaries: a tile's dominant term globally may be one this principal cannot satisfy, violating I2 — source: .ignore/tessera-architecture-design.md §7.4

## Cluster visibility (§7.5)

- The supplied hierarchy is used as a tree, not a flat partition, so insufficient visibility becomes rollup rather than suppression: store a membership bitmap per node, descend from the root evaluating `and_cardinality` against the mask, and stop when the visible count falls below threshold — source: .ignore/tessera-architecture-design.md §7.5
- The user's clustering is the frontier of that descent — coarse where they see little, fine where they see a lot; nobody gets a blank region, they get a vaguer ancestor — source: .ignore/tessera-architecture-design.md §7.5
- Restrict the descent to nodes whose extent intersects the viewport; membership bitmaps are entity-space, so each node also stores a bounding box per slice and its members' row-ID ranges per segment — the walk uses boxes to prune and ranges to intersect without a per-node entity-to-row gather — source: .ignore/tessera-architecture-design.md §7.5
- The governing threshold, `min_visible_members`, is a disclosure control — every displayed item is authorised either way, so it exists to bound the residual structural leak in C1: that a node's existence and shape derive from global density including items the principal cannot see — source: .ignore/tessera-architecture-design.md §7.5
- Name `min_visible_members` separately from anything the caller's clustering uses, and review it as a security control — source: .ignore/tessera-architecture-design.md §7.5
- Node geometry — centroid, hull, count — is recomputed per user from masked membership — source: .ignore/tessera-architecture-design.md §7.5

## Label gating and the containment frontier (§7.6)

- Labels are supplied by the caller with their generating sets (§2.4); the service gates them: a label is served iff its generating set is a subset of `M_auth` — one bitmap operation, `and_cardinality(G, M_auth) == |G|`, evaluated per request (I3), and decomposed across partitions per I13 — source: .ignore/tessera-architecture-design.md §7.6
- This rule is the compartment-lattice instance of the derivation axiom from multilevel database security (Appendix D); what appears unpublished is applying it to shared, precomputed, generated summaries served to differently-cleared viewers — source: .ignore/tessera-architecture-design.md §7.6
- A term is permission-homogeneous under I5: everyone satisfying T sees every item indexed under T, so a generating set of the form G = node ∩ postings(T) is satisfied by exactly those principals who satisfy T — no coverage fraction, no threshold to defend — source: .ignore/tessera-architecture-design.md §7.6
- If the two plugin functions disagreed about T, every such generating set would become unsound at the same instant and the containment test would still return true — source: .ignore/tessera-architecture-design.md §7.6
- The assumption that a typical node draws on a modest number of terms is unmeasured (§16) — source: .ignore/tessera-architecture-design.md §7.6
- Generating sets are immutable (I8), so ingest can never make a label unsafe — only stale; a deleted item drops out of every mask, so any generating set containing it fails containment for every principal — source: .ignore/tessera-architecture-design.md §7.6
- Where the caller supplies a nested chain of generating sets, the smallest element is contained in every larger one, so a single deletion can dark-ship a node's entire chain; the service notifies the caller of affected labels (§2.5) and falls through the ladder meanwhile — source: .ignore/tessera-architecture-design.md §7.6
- Shrinking a generating set to exclude deleted items is not automatically safe — the label was generated from content including the removed item — and requires explicit sign-off and an Appendix C entry — source: .ignore/tessera-architecture-design.md §7.6
- The frontier under filtering: the filter influences the frontier only through descent depth, never through containment (I3, I12) — source: .ignore/tessera-architecture-design.md §8.4
- The naive implementation gets the direction wrong: `M_sel ⊆ M_auth`, so filtered counts are never higher, and descending on `M_sel` against a fixed threshold stops earlier everywhere — filtering would make the frontier uniformly coarser, not finer around the hits — source: .ignore/tessera-architecture-design.md §8.4
- Two thresholds with different jobs: `min_visible_members` against `M_auth` sets the maximum depth and remains a disclosure control that filtering must not relax — the operational form of I12; a much smaller display threshold against `M_sel` decides how far within that bound to descend — to maximum depth where matches concentrate, stopping early over empty regions — source: .ignore/tessera-architecture-design.md §8.4
- Stability: the frontier recomputes on every filter change, so labels appear, refine and disappear as someone types; debounce, and add hysteresis so a node does not drop out because a match count wobbled by one — source: .ignore/tessera-architecture-design.md §8.4

## The fallback ladder (§7.7–7.9)

- Fallback ladder tiers, in order: full node label (generating set = entire node membership at generation time, supplied); cumulative-union labels (progressively larger unions, supplied); single-term labels (node ∩ postings(T), supplied); extractive term list (mask ∩ node, exactly the visible items, computed at view time); no label — source: .ignore/tessera-architecture-design.md §7.7
- The extractive tier is c-TF-IDF over the supplied per-item vocabulary vectors — source: .ignore/tessera-architecture-design.md §7.7
- Background document frequencies must come from a fixed public reference corpus, not from the live corpus — live frequencies are an aggregate over mostly unauthorised data and determine which terms are shown, violating I2 silently — source: .ignore/tessera-architecture-design.md §7.7
- The extractive tier's generating set is by definition inside the mask, so it always satisfies I3, and it is the only tier covering newly ingested items before the caller regenerates — source: .ignore/tessera-architecture-design.md §7.7
- Because only satisfied candidates are ever evaluated, a principal never learns of the existence of a label they cannot see; the decision to withhold is a function of data on their own side of the boundary, so the refusal itself carries no information — a property most suppression schemes lack (Appendix D) — source: .ignore/tessera-architecture-design.md §7.7
- Guidance for the caller's labeller (three decisions belonging to the caller's pipeline, constrained by the service's design): which generating sets to produce — the natural construction is a nested chain of cumulative unions ordered by term mass, supplemented by individual single-term sets — source: .ignore/tessera-architecture-design.md §7.8
- Which set to declare: if prompts are built from sampled members rather than whole nodes, "every item it was generated from" can mean the sample or full membership; settled (r17, owner decision): the prompt sample — it is honest to provenance and it is the available choice; full-membership declaration remains available per deployment as a strict mode — source: .ignore/tessera-architecture-design.md §7.8
- Label creep is the named, predicted failure mode: conservative joining over many sources drives the effective reader set toward empty; if nodes are formed on semantic similarity alone, most labels become unservable to almost everyone; per-term generating sets mitigate this by construction; the escalation if labels are still widely unservable is ACL-aligned clustering — partition by term-equivalence class first, cluster semantically within — source: .ignore/tessera-architecture-design.md §7.8
- Conditional optimisation: if the single-term fraction (§16) is high, precompute a sparse (term × tile) count matrix for coarse zoom levels; a visible count for a tile is then the sum over satisfied terms — a sparse matrix-vector product — with no mask materialisation at all — source: .ignore/tessera-architecture-design.md §7.9
- Counts sum rather than union exactly when items carry a single term; hold the single-term majority in the matrix and correct the remainder through the mask — source: .ignore/tessera-architecture-design.md §7.9
- At 10^7 this is a modest optimisation; at 10^9 it substantially dissolves the worst path in the system, where a zoomed-out overview otherwise forces every shard to materialise a mask fragment (§13.3) — source: .ignore/tessera-architecture-design.md §7.9
- The same structure can hold per-(term, tile) representative samples; every item so served is under a satisfied term, so I7 holds — source: .ignore/tessera-architecture-design.md §7.9

## The two-mask model (§8.1)

- `M_auth` — what the token permits (I1); governs label containment, maximum frontier depth, node geometry, and the security boundary — source: .ignore/tessera-architecture-design.md §8.1
- `M_sel = M_auth ∧ filter₁ ∧ … ∧ filterₙ` — what the query asked for; governs which points render and matched counts — source: .ignore/tessera-architecture-design.md §8.1
- The failure this prevents: with a single composed mask, containment would be tested against `M_auth ∧ text ∧ vector`; a generating set contains items that do not match the text query, so containment fails for essentially every label the instant anyone types, and every label vanishes — source: .ignore/tessera-architecture-design.md §8.1
- A frontier descending on filtered counts would likewise dissolve as the filter narrows, destroying the frame of reference exactly when it is most needed; I3 and I12 prevent both — source: .ignore/tessera-architecture-design.md §8.1
- There is no leak in preserving labels under filtering: the principal could already see them before filtering, and per I12 a filter cannot widen authorisation — source: .ignore/tessera-architecture-design.md §8.1
- A free affordance falls out: `range_cardinality` over both masks on the same range gives matched-and-visible against total-visible, exactly, for two bitmap operations — supporting highlight-in-context rather than removing everything else and leaving the user staring at twelve points on a blank canvas — source: .ignore/tessera-architecture-design.md §8.1

## The filter contract (§8.2) — order-independent set producers composed by intersection

- Every filter returns a set of entity IDs as a bitmap; composition is intersection; this is also the extension discipline for the retrieval surface: new filter forms add operands rather than changing the shape of the call (§2.2) — source: .ignore/tessera-architecture-design.md §8.2
- Rule: threshold, never top-k — a filter whose result depends on what else is in the query cannot be composed independently; a top-k nearest-neighbour query evaluated alone is computed over the whole corpus, so intersecting afterwards is post-filtering — the principal's nearest neighbours would vary observably with items they cannot see; express ranked filters as thresholds and apply top-k after intersection — source: .ignore/tessera-architecture-design.md §8.2
- Rule: optional candidate push-down — filters accept an optional candidate bitmap; those that can exploit it do, those that cannot ignore it; this makes vector brute-force viable and removes the post-filter leak in the same move — source: .ignore/tessera-architecture-design.md §8.2
- Rule: the mask goes in first, not last — it is usually the most selective operand, and every un-intersected intermediate contains unauthorised IDs — source: .ignore/tessera-architecture-design.md §8.2
- Rule: pre-intersection cardinality is structurally unreachable — a raw match count is a corpus-wide count over unauthorised records; do not let the pipeline expose a cardinality on an un-intersected intermediate at all — source: .ignore/tessera-architecture-design.md §8.2
- Keep it a pipeline, not a planner: intersection is the only top-level operator; fix the order at design time by cost class; statistics-driven reordering would make execution time a function of how much the principal can see — source: .ignore/tessera-architecture-design.md §8.2
- Where each filter lives: label filtering is core, effectively free — resolve labels to nodes, union membership bitmaps, intersect; the label vocabulary offered must itself be containment-filtered, or the existence of a filterable label reveals a label the principal is not cleared to see (C11) — source: .ignore/tessera-architecture-design.md §8.3
- Text is an embedded index; text results depend on the query, not the token, so they cache globally across all principals within a partition — a different key from the mask, and conflating the two yields either a cache that never hits or a leak; filter, do not rank — relevance scores and rank shifts computed from corpus-global statistics are a demonstrated channel for inferring the content of unreadable documents (Appendix D) — source: .ignore/tessera-architecture-design.md §8.3
- Vectors are a sidecar in a different format — cold, large, read in a completely different pattern from the hot columns — source: .ignore/tessera-architecture-design.md §8.3
- If label and text filtering plus the mask reduce the candidate set below roughly 10^5–10^6, brute-force scan the masked candidates — a few milliseconds with SIMD, and exact — source: .ignore/tessera-architecture-design.md §8.3
- Execution order: label → text → intersect with `M_auth` → brute-force vectors over survivors — source: .ignore/tessera-architecture-design.md §8.3
- One UX trap for the caller: the 2D coordinates are a projection; similarity in the source space is not similarity in the plane — source: .ignore/tessera-architecture-design.md §8.3

## Rendering and caching under filtering (§8.5)

- Two layers: a context layer sampled from `M_auth`, where coverage is normal and §7.2's candidate lists work as sized; and a match layer from `M_sel`, which under a selective filter is small enough to send in full, with no sampling and no descent — source: .ignore/tessera-architecture-design.md §8.5
- Sampling of `M_sel` is needed only when the filter is broad, and then coverage is good again — so the pathological case of a sparse mask requiring k-per-tile sampling does not arise — source: .ignore/tessera-architecture-design.md §8.5

## Compartmented partitions (§12)

- Some terms mark data that must be held separately at rest and in memory, not merely masked; a partition is a set of items sharing a required term set, stored in its own files and served by its own process — source: .ignore/tessera-architecture-design.md §12
- It is a second sharding axis — §13.3 shards by row range for scale, this shards by term for isolation — and the two compose — source: .ignore/tessera-architecture-design.md §12
- One distinction decides whether the design is valid at all: if the requirement is that data be separated (compartment A's items not co-resident with compartment B's), the design is correct; if the requirement is that audiences be separated (A-cleared and B-cleared principals must never touch the same hardware), then items spanning compartments must be rejected rather than placed — source: .ignore/tessera-architecture-design.md §12.1
- Settled (r17, owner decision): the requirement is data separation; the rest of §12 is operative, not conditional — source: .ignore/tessera-architecture-design.md §12.1
- A partition's required set is the intersection of compartment markers across every disjunct of an item's predicate — every route to the item, not merely one; if an item's terms are {a, R} and {b, R}, then R is genuinely required; if its terms are {a, R} and {b}, then R is not required, because the second term admits a principal without it — source: .ignore/tessera-architecture-design.md §12.2
- The gate: a token may query a partition only if it satisfies every term in the required set; this is exactly sound rather than merely conservative — a token satisfying any of an item's terms necessarily satisfies everything in the intersection, so the gate never excludes an authorised token, and it excludes only tokens that could not have satisfied any term — source: .ignore/tessera-architecture-design.md §12.2
- The mixed case falls out rather than needing a rule: an item with one uncompartmented disjunct has an empty intersection and lands in the default partition automatically; if any of its disjuncts carried a compartment marker, that marker is provably doing nothing — the item is reachable without it — so warn loudly; it is almost certainly a labelling error, but not a security violation, so it must not block ingest — source: .ignore/tessera-architecture-design.md §12.2
- Under the reference plugin (Appendix E) compartments map naturally onto the conjunctive dimension, whose semantics already are "must hold every one of these" — source: .ignore/tessera-architecture-design.md §12.2
- Everything keyed on entity partitions with the items: the term index, columns, permutation, tile table, candidate lists, node membership, generating sets, text index and vectors — source: .ignore/tessera-architecture-design.md §12.3
- Each partition has its own Morton ranking and its own row-ID space, which preserves the row-ID-is-the-array-index property that a sparse global ranking would destroy; node metadata — bounding boxes, extents, term distributions — is held per partition too — source: .ignore/tessera-architecture-design.md §12.3
- The mask never exists whole: each partition builds its own fragment from its own term index, so no process outside a compartment holds a bitmap containing its entity IDs — that is the isolation property, and it is why authorisation fans out — source: .ignore/tessera-architecture-design.md §12.3
- Counts sum: tile identity is geometric (§5.2), so partitions agree on which tile is which while mapping it to their own rank ranges — source: .ignore/tessera-architecture-design.md §12.3
- Priority sampling composes exactly: because priority is a global per-item property, the k lowest-priority visible items in a tile equal the k lowest of the union of each partition's k lowest; every partition runs §7.2 locally, including its own candidate-list descent, and the coordinator takes the global top k; the rank-position scheme rejected in §7.2 would not have composed, since rank positions are relative to a population — source: .ignore/tessera-architecture-design.md §12.3
- Containment decomposes: since generating sets and masks both partition by entity, G ⊆ M iff G_p ⊆ M_p for every p — subject to I13: a partition the token cannot reach counts as failing, never as vacuously satisfied; a label whose generating set has a non-empty slice in an unreachable compartment must be withheld, and the natural implementation gets this wrong — source: .ignore/tessera-architecture-design.md §12.3
- Partitions are discovered, not declared: when an item arrives with a previously-unseen required set, its partition is created; existing partitions are untouched — source: .ignore/tessera-architecture-design.md §12.4
- Identity is a canonical hash of the sorted required set, which makes creation idempotent and lets two ingest workers racing on the first item of a new combination converge rather than conflict — source: .ignore/tessera-architecture-design.md §12.4
- Alarm on creation: a new combination means either a data error or a policy change, and someone should look either way; silent creation is how the problem is discovered at 3am — source: .ignore/tessera-architecture-design.md §12.4
- Cap the count: a token fans out to up to 2^n − 1 partitions where n is the number of compartments it holds — exponential in a parameter someone may increase casually; each partition also carries fixed infrastructure overhead, and fan-out p99 is the slowest partition — source: .ignore/tessera-architecture-design.md §12.4
- A combined partition owes the union of its constituents' isolation requirements — if A mandates particular key management and B mandates a jurisdiction, the A+B store owes both; a further argument for keeping compartments coarse — source: .ignore/tessera-architecture-design.md §12.4
- Isolation strength is a ladder: separate process and address space with separate mmap'd files is the cheapest meaningful rung; adding a separate memory cgroup and no shared page cache closes core dumps and swap; a separate host with its own keys and operator access closes the rest — source: .ignore/tessera-architecture-design.md §12.4
- Changing the partitioning has two categories that look alike and cost differently by orders of magnitude: data changes (an item's predicate changes such that its required set changes, so it must move stores — the overlay covers visibility during the move: deny in the source, evaluate once landed in the destination) and policy changes (marking a previously-open term as compartmented, un-compartmenting one, changing a required set, splitting or merging compartments — every one requires re-evaluating placement for every affected item, including a global scan to find items that should now move in — that is a reindex, with no incremental path worth building) — source: .ignore/tessera-architecture-design.md §12.5
- The compartment map is a schema-level decision, not a runtime knob; the mitigation is already in the design: §10.2's immutable versioned prefixes mean a repartitioning is built under a new prefix and cut over by flipping a pointer — expensive, but not risky, and reversible — source: .ignore/tessera-architecture-design.md §12.5
