# Part 1 facts — aggregate leakage, demonstrated vs marketed scale, row-level ACL coverage, PostgreSQL RLS / DuckDB measurements

Format: one line per entry — CLAIM — source: `<file>` §`<section>`. Verbatim quotes given for every number and every third-party-system assertion, per instructions.

## Aggregate leakage in systems with per-document security

- Elasticsearch's own limitations page documents that a user with document-level security "could still... count how many inaccessible documents contain a given term," with scoring using corpus-global statistics that ignore the role query — source: prior-art-synthesis.md §4, "Elasticsearch is the only surveyed system with real per-document security, and its official limitations page states a user 'could still... count how many inaccessible documents contain a given term,' with scoring using corpus-global statistics that ignore the role query."
- Solr's `domain.excludeTags` is a supported, documented feature for computing facet counts outside the security filter, i.e. counts over documents the caller cannot read — source: prior-art-synthesis.md §4, "Solr is worse: `domain.excludeTags` is a *supported feature* for computing facet counts outside the security filter."
- Vespa and Quickwit have no per-document access control at all, so the question of aggregate leakage over inaccessible documents does not even arise as a boundary — source: prior-art-synthesis.md §4, "Vespa and Quickwit have no per-document access control at all."
- Every statistical-disclosure-control (SDC) tool surveyed transmits something about invisible records by design (perturbed counts, rounded figures, bounded intervals) rather than withholding entirely — source: prior-art-synthesis.md §4, "Every SDC tool transmits something about invisible records by design."
- Elastic's Document-level security (DLS) fails open in a specific documented way: omitting the `query` parameter entirely disables document-level security — source: prior-art-synthesis.md §5, "Elastic's DLS fails open in a specific documented way: omitting the `query` parameter entirely disables document-level security."
- Elastic's DLS role-query is cached as a Lucene BitSet used as a prefilter for approximate vector search, and the same documentation states omitting the `query` parameter entirely disables document-level security (fail-open) — source: prior-art-4-authorization-disclosure.md "Where an existing system could be adopted", "the role query 'cached as a BitSet' wrapping the Lucene reader such that 'DLS filtering works as a prefilter for approximate vector search'... Note its fail-open hazard: 'Omitting the `query` parameter entirely disables document level security.'"
- A fully patched PostgreSQL with row-level security (RLS) discloses the exact count of policy-excluded rows via `EXPLAIN ANALYZE` — source: prior-art-3-databases.md §4.2, "`EXPLAIN ANALYZE` reports `Rows Removed by Filter: 99000`" — the exact count of rows excluded by the policy.
- PostgreSQL RLS discloses the density of an invisible cluster at roughly 1,500× above background via a plain, unprivileged `EXPLAIN`, because planner statistics are computed over all rows and the relevant comparison operators are leakproof — source: prior-art-3-databases.md §4.2, "viewport x=[70,71)  EXPLAIN rows=4748    actual visible rows=50   <-- invisible cluster" against flat visible density elsewhere in the same table (rows≈3–6 elsewhere).
- PostgreSQL's own documentation concedes RLS is not a confidentiality boundary against inference from plans, timing or statistics, and effectively states that if this is a concern the right answer is to grant no access at all — source: prior-art-3-databases.md §4.1, "a user can see the plan, can measure run time, and 'might be able to infer something about the amount of unseen data, or even gain some information about the data distribution or most common values...' concluding: 'If these types of "covert channel" attacks are of concern, it is probably unwise to grant any access to the data at all.'"
- PostgreSQL `pg_class.reltuples` is unrestricted by RLS, so a caller reads the true total row count sitting next to a masked `pg_stats` — source: prior-art-3-databases.md §4.2, "`pg_class.reltuples` is unrestricted, so the analyst reads the true total row count sitting next to a masked `pg_stats`."
- CVE-2019-10130 ("Selectivity estimators bypass row security policies") shows PostgreSQL previously allowed a crafted leaky operator to read sampled data bypassing RLS, fixed by only allowing non-leakproof operators to use sampled statistics when relevant row-security policies exist — source: prior-art-3-databases.md §4.2, quoting the fix as "only allowing a non-leakproof operator to use this data if there are no relevant row security policies for the table," and the vulnerability as letting "a user able to execute SQL queries with permissions to read a given column craft a leaky operator that could read whatever data had been sampled from that column."
- The CVE-2019-10130 fix only gates non-leakproof operators; leakproof operators (e.g. `float8lt`/`float8le`, used in a viewport range query) still consult full-table histograms and disclose invisible-cluster density — source: prior-art-3-databases.md §4.2, "that fix gates only non-leakproof operators, and the entire viewport query is leakproof."
- BigQuery's own documentation admits a side channel: query duration can leak information about rows near storage-shard boundaries under row-level security — source: prior-art-3-databases.md §4.5, "'Side channels, such as the query duration, can leak information about rows that are at the edge of a storage shard'."
- Snowflake documents that with a row access policy, statistics-based optimisations "are not applicable," and that returned statistics reflect only what is permissible to access rather than "the 'true' statistical values" — source: prior-art-3-databases.md §4.5, quoting Snowflake as "the only vendor to state the correct semantics explicitly."
- Databricks Unity Catalog claims the query engine "always makes the secure choice" over optimisation when row filters are present, but this claim carries no published, independent verification — source: prior-art-3-databases.md §4.5, "'the query engine must choose between optimization and protecting against information leakage from filtered or masked values, it always makes the secure choice, which can affect query performance' — an assertion with no published verification."
- Microsoft GraphRAG builds shared, precomputed hierarchical-clustering "community reports" fed wholesale into global search, and has no permission model at all — none of its indexing, dataflow, global-search docs or the MSR announcement mention permissions, ACLs or multi-tenancy — source: prior-art-4-authorization-disclosure.md "Priority 1", "Microsoft GraphRAG builds exactly this artefact... and has no permission model at all."
- Apache Accumulo is, by contrast, the one system across the whole survey whose default read path does not leak counts/density/existence over unauthorised cells: every aggregating iterator is stacked structurally above the visibility filter and cannot observe what it filters — source: prior-art-3-databases.md §7.6, "Accumulo's default read path satisfies the hard requirement... This is a materially better security posture than every other system in this review."
- Accumulo's one real leak vector, "Summaries," computes label-occurrence counts per key range without being filtered by the caller's own authorisations, but this is gated behind a distinct, non-default permission (`GET_SUMMARIES`) not implied by `READ` — source: prior-art-3-databases.md §7.6, "it genuinely is 'counts per label over a key range', **not** filtered by the caller's authorizations... requires `TablePermission.GET_SUMMARIES`, a distinct permission not implied by `READ` and not granted by default."
- Büttcher & Clarke (USENIX FAST '05) proved post-filtering search results lets an attacker infer the content of unreadable files from relevance-score/rank shifts, recovering corpus term statistics from planted test files — source: prior-art-4-authorization-disclosure.md §7, "demonstrating that post-filtering lets an attacker infer content of unreadable files from 'the relevance scores or the relative ranks' — plant test files, watch BM25 shift, recover corpus term statistics."
- SharePoint's own documentation recommends pre-trimming over post-trimming specifically because post-trimming leaks refiner counts and hit counts — source: prior-art-4-authorization-disclosure.md §7, "recommending pre-trimming *specifically because post-trimming leaks refiner counts and hit counts*."
- No RAG paper found by the review cites Büttcher & Clarke's twenty-one-year-old proof that aggregate/rank information leaks unreadable content — source: prior-art-synthesis.md §3, "that is the 'not even aggregate counts' requirement, demonstrated as necessary twenty-one years ago, and no RAG paper cites it."
- Kenthapadi, Mishra & Nissim (PODS 2005) proved a refusal to answer is itself a leak channel whenever the refusal decision depends on data the requester cannot see — source: prior-art-synthesis.md §3, "a refusal is itself a leak channel whenever the refusal decision depends on invisible data."
- GeoServer's GeoWebCache (GWC) documents that data-security filters are off by default, and even enabled they support only geographic-boundary restrictions while "all other types of data access limits will be ignored," and that a CQL read filter is silently ignored by the tile cache — source: prior-art-2-visual-analytics.md §8, quoting GeoServer docs: GWC data security is "by default... turned off"; "limited support for data access limit filters, only with respect to geographic boundaries (all other types of data access limits will be ignored)"; "this behaviour is different from the regular WMS, which will filter the data before serving it."
- Azure AI Search is the only vendor surveyed documenting fail-closed behaviour on ACL-evaluation failure ("the service returns 5xx and does not return a partially filtered result set"); every other system documented fails open — source: prior-art-synthesis.md §5, quoting Azure AI Search: "the service returns 5xx and does not return a partially filtered result set."

## Demonstrated vs marketed scale, per visualisation system

- deepscatter's tagline is "scales over a billion points," its README's actual worked examples are 5.5 million tweets and 20 million biomedical abstracts, and its billion-point artefact (Schmidt's Gaia demo) is a static star catalogue with no masking — source: prior-art-2-visual-analytics.md §2, "Tagline: 'scales over a billion points.' README examples: **5.5 million tweets** and **20 million biomedical abstracts**... Honest demonstrated ceiling for the full stack: ~20M."
- Nomic Atlas's marketing says "billions," but its demonstrated scale is 11 million points (Obelics), "the largest interactive data map ever published," with other public maps at 5.4M tweets and 6.4M images; its own whitepaper admits "Nomic is unable to disclose many technical details of the Atlas system at this time" — source: prior-art-2-visual-analytics.md §3, "**Demonstrated scale:** **11 million points** (Obelics)... Marketing says 'billions'."
- Falcon is demonstrated at 10M records in-browser and 180M flights / 1.2B GAIA stars database-backed, but its per-user filtering is per-*view* only, none per-record, and its 10⁹ reach is via aggregation to summed-area-table bins, not identifiable points — source: prior-art-2-visual-analytics.md §4, "Demonstrated at **10M records in-browser**, **180M flights / 1.2B GAIA stars** database-backed. Trade: interaction with **a single active view only**."
- Nanocubes "takes up to 6 hours to build an index for a dataset with 210M objects," with memory growing combinatorially with dimensions and resolution — source: prior-art-2-visual-analytics.md §4, quoting Falcon's CHI paper: "takes up to 6 hours to build an index for a dataset with 210M objects."
- Hashedcubes (via secondary paper notes, not independently verified) achieves ~5.2× memory reduction vs Nanocubes — 9.4 GB vs Nanocubes' 46.4 GB — with most queries under 40 ms — source: prior-art-2-visual-analytics.md §4, "~5.2× memory reduction vs Nanocubes — 9.4 GB where Nanocubes needed 46.4 GB, most queries under 40 ms."
- Mosaic is demonstrated at 10M rows static rendering, and at 10M/100M/1B rows plus the 1.8B-row GAIA catalogue for interactive updates, with index construction under 5 seconds for 200M records and ~100ms interactive latency; but DuckDB-WASM failed on the 1B-row flights data and on large GAIA samples due to WebAssembly memory limits, and Mosaic answers 10⁹ points via rasterization (density rasters, hex binning) rather than sampling identifiable points — source: prior-art-2-visual-analytics.md §5, "Static rendering benchmarked to **10M rows**. Interactive updates on flights at **10M / 100M / 1B rows** and the **1.8B-row GAIA catalogue**... DuckDB-WASM failed on the 1B-row flights data and on large GAIA samples due to WebAssembly memory limits."
- Apple's Embedding Atlas publishes real benchmarks on stated hardware: on an M1 Pro at 1600×1600, up to 4M points at 60fps and 10M+ points at 25fps, but its philosophy is explicitly brute force ("no need to pre-sample or pre-render your data") and it caps around 10⁷ with no server-side filtering seam — source: prior-art-2-visual-analytics.md §7, "on an M1 Pro at 1600×1600, up to 4M points at 60fps and 10M+ points at 25fps"; "'no need to pre-sample or pre-render your data.'"
- TensorBoard's Embedding Projector has a hard `LIMIT_NUM_POINTS = 100000` and — the review calls out as worse — returns the first 100,000 rows, not a sample, per the project's own GitHub issue — source: prior-art-2-visual-analytics.md §7, quoting issue #773 finding: "returns the first 100,000 rows, not a sample."
- FiftyOne's team's own working number is 500K points; its "progressive loading" delivers linear 100K chunks in wire order (a partial load is a random-looking subset), which the review calls strictly weaker than a quadtree partial-load; access control is per-dataset only — source: prior-art-2-visual-analytics.md §7, "**Team's own working number is 500K.**"
- Renumics Spotlight (MIT, v1.8.0) has no demonstrated point count published anywhere, and no tiling or auth — source: prior-art-2-visual-analytics.md §7, "**no demonstrated point count published anywhere**. No tiling, no auth."
- Bunka uses d3/SVG with no WebGL at all; its largest demo is ~29k points, and its last release was May 2024 (inactive) — source: prior-art-2-visual-analytics.md §7, "**no WebGL at all**; largest demo ~29k points. Last release May 2024, inactive."
- Cohere's semantic-search cookbook UMAPs exactly 1,000 rows into Altair, despite marketing material describing "search 10 million Wikipedia vectors" (a retrieval claim, not a rendering claim) — source: prior-art-2-visual-analytics.md §7, "UMAPs exactly 1,000 rows into Altair. Beware 'search 10 million Wikipedia vectors' material — that is retrieval, not rendering."
- Nobody surveyed has demonstrated 10⁹ identifiable, filterable, labelled points: Falcon and Mosaic reach 10⁹ by aggregating to bins, deepscatter reaches it only on a static star catalogue with no masking — source: prior-art-synthesis.md §7, "nobody has demonstrated 10⁹ identifiable, filterable, labelled points — Falcon and Mosaic reach 10⁹ by aggregating to bins, deepscatter reaches it on a static star catalogue with no masking."
- The NeurIPS'23 Big ANN filtered-search track — described as the field's flagship filtered-retrieval benchmark — used a 200,386-tag vocabulary but each query carried "one image embedding and one or two tags," four orders of magnitude below the ~10⁴ terms per query this design needs — source: prior-art-3-databases.md §2, quoting the paper: "one image embedding and one or two tags."

## Row-level access control coverage across the visualisation category

- Nomic Atlas's access control is org- and dataset-level only, with no per-record concept anywhere; "access controlled datasets" means the whole dataset is private, not that rows are masked per viewer — source: prior-art-2-visual-analytics.md §3, "access control is **org- and dataset-level only**... No per-record concept anywhere."
- Mosaic has no row-level security, multi-tenancy, or access control at all — its architecture is "trusted client issues arbitrary SQL to your database" — source: prior-art-2-visual-analytics.md §5, "**No row-level security, multi-tenancy or access control** — the architecture is 'trusted client issues arbitrary SQL to your database'."
- "Row-level access control across this entire category: zero systems. The granularity ceiling is universally the dataset." — source: prior-art-2-visual-analytics.md §7 (verbatim heading/claim), also restated in prior-art-synthesis.md §4: "Row-level access control across the entire visualisation category: zero systems. Not one. The granularity ceiling is universally the dataset."
- The MVT (Mapbox Vector Tile) spec offers no security seam at all: grepping the spec for security/auth/user/permission/access/encrypt returns zero hits, so all per-user variation must live outside the tile format — source: prior-art-2-visual-analytics.md §8, "Grepping vector-tile-spec 2.1... for *security, auth, user, permission, access, encrypt* returns **zero hits**."
- Every geospatial vector-tile system surveyed degrades to one of three exits: bypass the cache entirely for authenticated requests (Tegola never caches parameterised maps at any zoom), publish one static artefact per permission class (pg_tileserv, Esri — with Esri warning that once a tile layer's view definition is published it cannot be modified or removed, so authorisation changes never propagate to already-baked tiles), or reject rather than filter (GeoServer/GeoWebCache) — source: prior-art-2-visual-analytics.md §8, "Every system degrades to one of three exits: 1. **Bypass the cache**... 2. **One artefact per permission class**... 3. **Reject rather than filter**."
- Esri explicitly documents that "once the tile layer is published, you cannot modify or remove the view definition," meaning data changes propagate to tiles but authorisation changes do not — source: prior-art-2-visual-analytics.md §8, "with the vicious detail that *'once the tile layer is published, you cannot modify or remove the view definition.'* Data changes propagate to tiles; **authorisation changes do not.**"
- Supabase's PostGIS vector-tile pattern is architecturally the cleanest constructive exception found (an `mvt(z,x,y)` PostgREST function running with invoker rights so RLS applies inside the tile function), but its demonstrated policy is only `USING (true)` and it does not discuss caching — an existence proof, not a blessed pattern — source: prior-art-2-visual-analytics.md §8, "an existence proof, not a blessed pattern."
- GeoServer's unreleased/undocumented `AccessLimitsKeyBuilder` on `main` serialises a user's AccessLimits (including ECQL read filters) into a stable cache-key component with `securityTags` for targeted invalidation — directional evidence the industry now treats cache-partitioning-by-authorisation as the right answer, but it is unreleased and undocumented — source: prior-art-2-visual-analytics.md §8, "**unreleased and undocumented**, but directional evidence that the industry now considers cache-partitioning-by-authorisation the right answer."
- Zilliz (Milvus) publishes a row-level RBAC pattern (per-row array of role strings filtered with `array_contains_any()`) that is architecturally this design's problem at 1/1000th scale, capped at `max_capacity=10` roles per row — source: prior-art-3-databases.md §2, "Zilliz publishes a row-level RBAC pattern that is *literally this architecture*... with the schema capped at **`max_capacity=10`** roles per row."
- Milvus's partition-key multi-tenancy (hash-and-modulo of a scalar) is structurally 1:1, and Milvus's own docs concede it gives "relatively weak data isolation," not a security boundary — source: prior-art-3-databases.md §2, quoting Milvus docs conceding partition-key multi-tenancy gives "relatively weak data isolation."
- Not one of the six vector databases surveyed (Milvus, Qdrant, Weaviate, Pinecone, Turbopuffer, Vespa) caches a per-user filter bitset across queries, and every one of their multi-tenancy models is fundamentally 1:1 (one namespace/partition per tenant) rather than per-row ACL — source: prior-art-3-databases.md §2, "The cross-cutting negative result: not one of the six caches a per-user filter bitset across queries... every multi-tenancy model is 1:1."
- Turbopuffer's docs actively instruct users to "create one namespace per set of documents... rather than using filters," i.e. row-level filtering is explicitly discouraged in favour of dataset/namespace-level partitioning — source: prior-art-3-databases.md §2, quoting Turbopuffer's docs instruction to "create one namespace per set of documents… rather than using filters."

## PostgreSQL RLS — original measurements (review 3, §4)

- Test configuration: 10⁷ rows, `cats int[]` with 10 categories each drawn from 10⁵, a 10⁴-element allow-list per user, GiST index on `point(x,y)`, GIN index on `cats`, `shared_buffers=512MB`, warm cache — source: prior-art-3-databases.md §4.3.
- Without RLS (superuser), the viewport query (1% of area, 984 rows) uses a Bitmap Index Scan on the GiST index and completes in 26 ms — source: prior-art-3-databases.md §4.3, table row "no RLS (superuser) | Bitmap Index Scan on GiST, **26 ms**".
- With RLS enabled via policy `cats && my_cats()` (a STABLE SQL function), the same query becomes a Seq Scan and does not complete in over 120 seconds — source: prior-art-3-databases.md §4.3, "RLS, policy `cats && my_cats()` (STABLE SQL fn) | Seq Scan, **>120 s, did not complete**".
- With RLS via a policy using a correlated subquery (`cats && (SELECT array_agg(cat) ...)`), the query becomes a Seq Scan and does not complete in over 180 seconds — source: prior-art-3-databases.md §4.3, "RLS, policy `cats && (SELECT array_agg(cat) ...)` | Seq Scan, **>180 s, did not complete**".
- With RLS via an `EXISTS (SELECT 1 FROM user_cats ...)` policy, the query completes via a Seq Scan plus a SubPlan executed 10⁷ times, in 86,803 ms — best measured RLS variant, still a ~3,340× regression vs the no-RLS baseline — source: prior-art-3-databases.md §4.3, "RLS, policy `EXISTS (SELECT 1 FROM user_cats ...)` | Seq Scan + SubPlan × 10⁷, **86,803 ms**"; and §4.6, "the best variant is a 3,340× regression."
- The structural cause is that `<@(point,box)` is not marked leakproof, so under RLS the planner cannot use it as an index condition ahead of the security qual, and the spatial (GiST) index is abandoned entirely; GIN on `cats` does not help because a 10⁴-key `&&` scan touches ~65% of the table — source: prior-art-3-databases.md §4.3, "`<@(point,box)` is not leakproof, so the planner may not use it as an index condition ahead of the security qual and **the spatial index is abandoned entirely**... GIN on `cats` does not help — a 10⁴-key `&&` scan touches ~65% of the table."
- A direct empirical test of `LEAKPROOF` marking: over a 100,000-row table with 1,000 visible rows, a default (non-leakproof) function is called 1,000 times (visible rows only), while a `LEAKPROOF`-marked equivalent (with artificially low cost to force early evaluation) is called 100,000 times against the full table (full disclosure) — source: prior-art-3-databases.md §4.1, table: "default (not leakproof) | 1,000 | visible rows only" vs "`LEAKPROOF` | 100,000 | full disclosure".
- `pg_stats` has been patched (2015) to exclude rows for tables with active row security, confirmed by direct test: an analyst role sees zero rows in `pg_stats` for such tables — source: prior-art-3-databases.md §4.2, "confirmed, an analyst role sees zero rows there," referencing the code guard "AND (c.relrowsecurity = false OR NOT row_security_active(c.oid))".
- Three separate CVEs (CVE-2016-2193, CVE-2023-2455, CVE-2024-10976), spanning 2016 to November 2024, all fix variations of the plan cache incorrectly reusing an RLS plan generated under a different role — a recurring, not one-off, class of bug — source: prior-art-3-databases.md §4.4, quoting each CVE description in turn, and "caching anything derived from an RLS policy across a role change has been gotten wrong three times, most recently in November 2024."

## DuckDB — original measurements (review 3, §5)

- Test configuration: DuckDB 1.5.5, Python client, 2 vCPU / 7 GB, `threads=2`, on-disk; synthetic corpus at 10⁵/10⁶/10⁷ rows, each row an `id BIGINT` plus a 10-element `INTEGER[]` drawn from a 10⁶-value domain; probe set of 9,948 distinct IDs giving 9.5–9.6% selectivity — source: prior-art-3-databases.md §5, "DuckDB 1.5.5... Synthetic corpus at 10⁵/10⁶/10⁷ rows... probe set 9,948 distinct IDs giving **9.5–9.6% selectivity**."
- DuckDB's "roaring" compression is a validity-mask compression codec (`PRAGMA force_compression='roaring'`, from v1.2.0), using a container size of 2048 rather than Roaring's standard 65,536 — meaning it is not format-compatible with CRoaring in either direction, and there is no queryable roaring bitmap type (`duckdb_functions()` filtered for '%roar%' returns nothing) — source: prior-art-3-databases.md §5.1, "`ROARING_CONTAINER_SIZE = 2048`, not Roaring's standard 65,536... the on-disk representation is not format-compatible with CRoaring in either direction... returns **nothing**."
- `list_has_any` over a LIST column is measured as disqualifyingly slow: at 10⁵ rows it takes 583 ms with a 10-element probe, 4,917 ms with a 1,000-element probe, and 39,637 ms with a 10,000-element probe; at 10⁶ rows with a 100-element probe, 5,097 ms; at 10⁷ rows with a 100-element probe, 58,127 ms — source: prior-art-3-databases.md §5.2, table with columns n/probe/time as quoted.
- Extrapolating `list_has_any` to 10⁷ rows × 10⁴ probe gives an estimated ≈1.1–2.1 hours on 2 cores, and at 10⁹ rows, an estimated "days" — source: prior-art-3-databases.md §5.2, "Two independent extrapolations to 10⁷ rows × 10⁴ probe agree at **≈1.1–2.1 hours on 2 cores**; at 10⁹ rows, days."
- The correct formulation — pre-exploding to an `(id, category_id)` pair table and using a hash semi-join — measures dramatically faster: 221 ms for `unnest` + `SEMI JOIN` count at 10⁶ rows, 167 ms for `unnest` + `IN (subquery)` at 10⁶ rows, 2,020 ms for `SEMI JOIN` count at 10⁷ rows, 1,673 ms for a `SEMI JOIN` count over a pre-built 10⁸-pair table, and 8,833 ms / 277 MB to build that 10⁸-pair table — source: prior-art-3-databases.md §5.3, full table as quoted.
- This semi-join formulation is roughly 3,000× faster than `list_has_any` at 10⁶ rows — source: prior-art-3-databases.md §5.3, "**~3,000× faster than `list_has_any` at 10⁶ rows.**"
- Extrapolating the semi-join approach to 10⁹ rows / 10¹⁰ pairs gives an estimated ~28 GB of DuckDB storage and ~170–200 s on 2 cores (roughly 10–25 s on 16–32 cores) — explicitly flagged as arithmetic extrapolation, not a measurement, since nothing above 10⁸ pairs was actually measured — source: prior-art-3-databases.md §5.3, "Extrapolating to 10⁹ rows / 10¹⁰ pairs: ~28 GB of DuckDB storage and ~170–200 s on 2 cores... **Not measured above 10⁸ pairs — that is arithmetic, not a result.**"
- ART indexing cannot be built on a LIST column at all (`InvalidTypeException: Invalid Type [BIGINT[]]: Invalid type for index key`); on the exploded scalar column it is legal but pointless — building one over 10⁸ rows took 82.8 s, and DuckDB's own indexing guide says index scans are only chosen below `MAX(2048, 0.001 × cardinality)`, roughly 96× below the mask build's actual ~9.6% selectivity — source: prior-art-3-databases.md §5.4, "building one over 10⁸ rows took 82.8 s... about 96× above that threshold."
- DuckDB's `rowid` documentation explicitly warns against using it as an identifier ("It is strongly advised to avoid using rowids as identifiers"), notes it is based on physical storage, stable only within a transaction, and that deletions introduce gaps — source: prior-art-3-databases.md §5.5, quoting the SELECT docs directly as cited.
- Warm in-process latency floor measurements: `SELECT 1` takes 0.217 ms; a point lookup on 10⁸ rows takes 1.177 ms; a 2,000-row range scan on 10⁷ rows takes 1.243 ms — source: prior-art-3-databases.md §5.6, "`SELECT 1` = 0.217 ms; point lookup on 10⁸ rows = 1.177 ms; 2,000-row range scan on 10⁷ rows = 1.243 ms."
- DuckDB has no `range_cardinality`, no `rank`, and no `select`-by-rank primitive over its `BITSTRING` type; `bitstring_agg` converted 957,733 IDs into a 10⁷-bit bitstring in 13.4 ms and `bit_count` ran in 5.5–17.2 ms, but `BITSTRING` is uncompressed, so a 10⁹-bit mask costs 125 MB — source: prior-art-3-databases.md §5.8, "`bitstring_agg` turned 957,733 IDs into a 10⁷-bit bitstring in 13.4 ms and `bit_count` ran in 5.5–17.2 ms... 10⁹ bits = **125 MB per mask**."
- The community extension `Smallhi/duckdb-roaringbitmap` contains no roaring bitmap code at all — it is an unmodified DuckDB extension template ("quack(name)"), one star, two commits, `grep -ci roaring` returns 0 — source: prior-art-3-databases.md §5.9, "Its only source file is the unmodified DuckDB extension template implementing `quack(name) → \"Quack {name} 🐥\"`... `grep -ci roaring` returns **0**."
- DuckDB's verdict from the review: viable as a mask-build tier (via the pre-exploded pair-table + hash-semi-join schema), better suited to it than `pg_roaringbitmap`, but not obviously worth the dependency versus a hand-rolled Rust kernel over already-mmap'd Arrow files — source: prior-art-3-databases.md §5.11, "Viable as the mask-build tier, better suited to it than `pg_roaringbitmap`, but not obviously worth the dependency."

## Expected-but-absent claims (noted per instructions)

- None of the four source files contains a claim that any surveyed visualisation or database system implements true "sample after per-user masking, nested across zoom" at the design's target scale — the sources are explicit that only tippecanoe's `--retain-points-multiplier` comes close, and even that degrades once mask pass-rate falls below ~1/N. No further absent-claim gaps were identified relative to the four requested topics; all four topics are directly and repeatedly addressed in the source material.
