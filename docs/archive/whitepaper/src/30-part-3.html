Part III

Turning permission into arithmetic

The previous part established the two coordinate systems and the cost model. This is where a viewer's grants stop being policy and become a bitmap — built once, cached, and thereafter intersected with everything the map does.

7. The plugin boundary

The engine holds one idea about authorisation and nothing else. An item carries a set of opaque term IDs; a token carries a set of satisfied term IDs; the item is visible to the token if and only if those two sets intersect. Everything about how those term sets are derived sits behind two caller-supplied functions, and the authorisation schema is deliberately out of scope for the service, which never receives policy semantics, only opaque terms.

The two functions are asymmetric by design. terms_of_label(item_label) runs once per item at ingest and must be fast; terms_of_auth(auth_data) runs once per authorisation and may be expensive. Both emit opaque byte strings, which the service interns into IDs in a shared, append-only namespace, so agreement between the two functions is nothing more than byte-equality of canonical descriptors. Beyond the consistency requirement of invariant I5, the plugin author owes four obligations: canonical descriptors, determinism, declared cardinality bounds, and respect for that cost asymmetry.

Each half has a name in the literature worth keeping, because each brings a body of work with it. The data function's normalisation of an item's predicate into terms is boolean expression indexing — indexing a collection of boolean predicates so that, given one assignment, every predicate it satisfies can be found. The auth function's job is partial evaluation producing a residual policy in disjunctive normal form, which is why driving authorisation from a policy engine later is a matter of writing one plugin rather than a redesign. And where a deployment needs compartments — sets of items sharing a required term set, gated by an intersection test — the established name is compartmented / lattice-based mandatory access control; dominance.

The reference plugin makes the shape concrete. Item predicates are written as access expressions in the accumulo-access grammar: tokens combined with & and |, parentheses for grouping, and no negation — so the predicate is monotone, DNF normalisation terminates and the term index is sound. Consistency then reduces to one rule: an item is indexed under its DNF terms and nothing finer, so a conjunctive disjunct is interned as a term in its own right and the item does not appear in the postings of that disjunct's constituent parts.

The risk in that construction is known rather than hypothetical. Fontoura et al., in the boolean expression indexing work published at SIGMOD 2010, measured DNF normalisation over Yahoo's ad-serving expressions and found it infeasible beyond nesting depth 2. Treating that workload as comparable to a corpus of access expressions is this design's judgement and not a claim the paper makes; taken as a warning, the mitigation is plugin-side minting of synthetic terms for deep subexpressions, which keeps terms per item linear in expression size at any nesting depth. Expansion itself was not measured in Phase 0, because here it cannot be — a deployment's predicates are its own knob. Both ends of the conservation law minting trades along were measured instead: satisfied terms per token to 104, terms per item to 1,000.

Both functions ship as wasm32 modules with no WASI imports — instantiation refuses any — so determinism is environmental rather than promised: there is no clock and no ambient capability to reach for. A plugin therefore cannot check expiry, and instead surfaces a credential's not_after for the host to enforce; nor is there online revocation, which is bounded by assertion lifetime instead. Shipping the two functions as separate modules keeps their blast radii apart: rotating trust anchors changes only the auth plugin's hash, which invalidates cached masks, and never the data plugin's, which is a full-reindex event.

Failure is fail-closed in the Non-Truman model sense — refusing rather than silently filtering. A trap or structurally malformed output fails the operation; an empty term list, by contrast, is valid, and means default deny on the label side and a zero-visibility token on the auth side. Declared cardinality bounds only warn: a predicate is a monotone disjunction, so more terms means broader intended visibility, and excluding on a bound would answer “visible to many” with “visible to none”.

What the core does with the resulting term IDs is index them. The term index maps each term to a Roaring bitmap of entity IDs, and Roaring's per-block encoding makes the badly skewed size distribution harmless: head terms become run containers, the long tail small sorted arrays. Mask construction then happens once per distinct auth input, unioning the posting lists of the satisfied terms — per partition the token can reach — into one bitmap in entity space. That union, the term index, label containment, level of detail, filters, partitioning and storage never learn where terms came from; only the derivation did.

That the postings are pre-exploded into an (entity_id, term_id) pair relation and joined as a semi-join is a requirement, not an optimisation. The natural alternative — hold terms as a list column and test containment against the presented set — is roughly three orders of magnitude slower in every implementation measured, because containment operators rebuild a probe structure per row. Even the semi-join is too slow for the authorise path at scale and is reassigned away from it: 3.9–10.3 s at a tiled 249.5M corpus, against a postings union 4–540× faster at 36–530 ms. At the full 109 corpus that union costs 230.6 ms for a category-like head grant set (9 terms, mask cardinality 264.3M) and 588.0 ms for 10,000 randomly drawn category-like grants (41.6% coverage, mask cardinality 416.1M) — the realistic worst case, and inside the 0.14–2 s band projected from the 250M measurements. Every timing in this paper was taken on WSL2 with 12 cores, 39 GB and an RTX 3080; the ratios are the evidence, the absolutes a starting point.

This is the two-stage split the service's API is built around. Authorise resolves the caller's authoritative auth data to satisfied terms, builds the mask and returns an opaque token, once per distinct auth input. Retrieve accepts that token plus a query and returns a rendered payload in single-digit milliseconds, many times per second while a user pans, because it works against a precomputed mask rather than re-deriving authorisation. Masks — though not tokens — are content-addressed on the satisfied term set, the auth plugin's version and the identity of the postings they were built from, so nothing invalidates an entry: a changed input is a different key. The auth data is kept alongside, so an evicted mask is rebuilt rather than failing at an arbitrary moment.

Outward, the boundary is narrower still: entity IDs never cross it at all (I10), and clients receive per-session opaque handles instead.

8. Signature-sorted entity IDs

Union cost is not a function of how many entities a mask contains but of how many Roaring containers the granted posting lists span — containers touched, not cardinality. That single fact makes the ordering of entity IDs an engineering decision rather than an implementation detail, because the ordering determines whether a term's members fall into a few containers or are smeared across all of them.

The measurement is stark. At equal coverage and equal mask cardinality, a label shape whose terms span roughly 37 densely-filled containers beats one whose terms span about 15,259 containers — all of them — at around 6.5 postings per container: 400× fewer container visits, and entity-space contiguity worth up to about 130× on union cost as a result. Cost is close to linear in containers spanned, the per-container constant drifting up only about 2× across 400× of scale, from 54 ns at 2.42M entities to 114 ns at 109.

Entity IDs are allocated in append-only batches, and the order within a batch is a free choice the design spends deliberately: assign IDs sorted by term signature — the set of terms the item carries — so that each term's postings form long runs inside that batch's ID range and head terms encode as run containers rather than scattered arrays. It costs nothing, weakens no invariant, and is safe only because entity IDs never leave the service.

Two results bound the payoff. Assignment in created order buys nothing at all: run lengths of 1.00–1.26 against a 1.000 random baseline. Signature-sorted assignment buys 8.9–36.7× on posting storage and up to 130× on union cost at equal coverage — for category-like labels, total posting storage from 7.7 MB to 0.9 MB; for a hash label shape with 100 terms, from 552.9 MB to 15.1 MB, with the cached 25%-coverage session fragment falling from 303 KB to 0.2 KB. For a surname-like shape it buys nothing measurable: like signature alignment and union speed generally, the headline follows the shape of the labels rather than the size of the corpus. These are floors rather than ceilings — at 2.4M items the mean category group holds 44 entities, so its runs are short; at 109 the groups are roughly 400× longer.

The gain is confined to entity space: the row-space mask — the same visible set permuted into Morton order — stays scattered regardless of how entity IDs were assigned. That is why the kernel carries two union algorithms, a Roaring n-way union costing O(terms × containers spanned) for the dense-bitmap regime and a concatenate-radix-sort-construct path costing O(total postings) for the sparse-array regime.

What makes this more than a tuning parameter is invariant I9:

I9 — Entity IDs are append-only and never reused. Masks and generating sets are sets of entity IDs held in caches with non-zero lifetime; reissuing a deleted item's ID grants the new item every access the old one had.

An ID, once assigned, is that item's ID for the lifetime of the corpus. There is no later pass that renumbers entities for better compression, because renumbering is reuse and reuse is a grant of someone else's access. The compression comes entirely from the ordering, so it ships in the first allocator or not at all: created-order IDs would lock in an uncompressed index until a full re-allocation rebuild of the corpus.

One ordering is specifically forbidden. Assigning entity IDs in Morton order is tempting, since it would make the entity-to-row permutation the identity; it is rejected because it would give permission-space IDs spatial meaning, turning the ID gap between two visible points into an estimate of unauthorised data nearby. Why signature ordering is safe and Morton ordering is not comes down to invariant I10:

I10 — Entity IDs never cross the trust boundary. They are dense and assigned in ingest order, so the gap between two visible IDs is a count of unauthorised items ingested in the same window. Clients receive per-session opaque handles instead.

9. One query, end to end

With the mask built, a viewport request is arithmetic over two bitmaps and a permutation. The specification's retrieve path runs to eleven steps; five carry the load, and they are worth following in order.

One. The viewport arrives: a rectangle at a zoom depth, pinned once to a segment-set version that is then used for the tile table, the columns, the permutation and the candidate lists alike, so that everything in the request sees one consistent geometry. The mask fragment carries its own watermark rather than sharing that pin, because a pin fixes geometry and must never fix authorisation.

Two. The rectangle is decomposed into a few hundred quadtree tiles at the target depth. By the Morton prefix property each tile is a contiguous half-open row range [lo, hi) — this is the whole reason for storing geometry in Morton order, and it is what converts a spatial question into an interval question.

Three. The effective mask is composed in entity space and projected into row space. Composition is M_auth = (M_token \ L) ∪ direct_eval(L), where L is the overlay unioned with every entity at or above the watermark; the frozen mask is read through a view over the memory-mapped file, with no deserialisation and no allocation. Filters narrow it by intersection, never touching authorisation. Projection then gathers entity_to_row[e] into a flat buffer, radix sorts it and bulk-constructs the row-space bitmap — the only point in the system at which the two ID spaces meet, and cached per (token, slice, pin) because it is the one expensive step.

Four. Each tile's row range is intersected with that row-space bitmap. intersect_with_range culls the empty tiles outright. Cost here is in containers, not rows.

Five. range_cardinality gives the exact masked count per tile, with no data file touched at all. Only then does selection happen, and that count is what decides how: at or below the per-tile budget take everything, above it take the lowest-priority visible items, evaluated directly from the mask where coverage is low or through a precomputed candidate list where it is high. Priority is a hash-derived per-point constant and is mask-independent, so the sample is a sample of the visible set rather than the visible portion of a global sample.

What follows is mechanical. The selected row IDs collect into one sorted u32 array, so the gather over the memory-mapped Arrow columns is forward-sequential-with-gaps; row IDs then translate to entity IDs and to per-session opaque handles on the way out. Labels are served separately, gated on M_auth and never on the filtered mask.

Three properties carry this design. Counting and post-mask sampling are both bitmap arithmetic over contiguous ranges, so cost scales with screen area rather than corpus size. Projection is the sole meeting point of the two ID spaces, which makes their separation a type rule rather than a convention. And nothing between mask composition and handle translation reads a column except through a masked row-ID set — which is invariant I2, that every derived quantity be a function of visible data only, in structural form rather than as a discipline.
