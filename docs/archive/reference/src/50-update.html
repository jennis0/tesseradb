Three things can happen to an item that is already being served: it can be deleted, an administrator can suppress it, or its access predicate can be edited. Each is handled by its own mechanism, and the whole point of the figure below is that they are three mechanisms and not one.

The three retirement rules, one row each.
Change What creates the entry Reflected in the index? What removes it The failure the rule prevents
Deletion The item is tombstoned; a deny entry is added, stamped with the tombstone epoch d. Yes — a tombstone applies immediately, and compaction folds it into the base. The epoch ledger: only once no servable cached view was built before d. A cached view built before the deletion may still be in service; dropping the entry while one survives would show the deleted item again.
Suppression An administrator suppresses the item; a deny entry is added, carrying no epoch. Never — a suppression does not touch the postings in any way. An explicit unsuppress, and nothing else: no timer, no epoch, no compaction event. An expiring entry would re-expose a hidden item with no operator action and no unsuppress — fail-open, and with no signal in the index to re-derive the state from.
Permission change The access predicate is edited; an evaluate entry is added, carrying the item's new term set inline. Not until compaction folds it, and in neither direction until then. The compaction fold, which stamps a fold epoch f; the entry then retires under the same ledger rule as a deletion's d. A view built before the fold still carries a revoked term (fail-open) and is missing a granted one (wrong counts).
