Tessera: the four processes

Single-page walkthroughs of ingest, authorisation, query and update — naming the actual structures, the order they are touched, and the optimisations that are load-bearing rather than incidental. This is the companion to the white paper: that document argues why the system is built this way, this one records what is built.

Status. The architecture is specified in full and Phase 0 is measured; Phase 1 is in progress. Where a step here is a design decision that no code yet implements, it is written in the present tense like the rest — this page describes the specification, not a running system. Every structure named traces to the design corpus, and section references point at the governing document.

Ingest — how data gets in

Ingest is an append: an arriving item is given a fresh identity above everything already allocated, and nothing that already exists is rewritten. The diagram follows one item in, and keeps apart the clocks — per item, per flush, per compaction — that are the easiest thing here to conflate.

Authorisation

Authorisation turns a viewer's credentials into one bitmap — the set of items that viewer may see — and does it once, at the start of a session. Everything the viewer does afterwards is arithmetic against that bitmap.

Query

A pan or a zoom is a viewport, and a viewport is a few hundred aligned quadtree tiles, each of which is one contiguous run of row IDs. Everything expensive — building the viewer's visible set and carrying it from entity space into row space — has already happened once for the session, and the per-viewport path is bitmap arithmetic over ranges.

Update

Three things can happen to an item that is already being served: it can be deleted, an administrator can suppress it, or its access predicate can be edited. Each is handled by its own mechanism, and the whole point of the figure below is that they are three mechanisms and not one.

The three retirement rules, one row each.
Change What creates the entry Reflected in the index? What removes it The failure the rule prevents
Deletion The item is tombstoned; a deny entry is added, stamped with the tombstone epoch d. Yes — a tombstone applies immediately, and compaction folds it into the base. The epoch ledger: only once no servable cached view was built before d. A cached view built before the deletion may still be in service; dropping the entry while one survives would show the deleted item again.
Suppression An administrator suppresses the item; a deny entry is added, carrying no epoch. Never — a suppression does not touch the postings in any way. An explicit unsuppress, and nothing else: no timer, no epoch, no compaction event. An expiring entry would re-expose a hidden item with no operator action and no unsuppress — fail-open, and with no signal in the index to re-derive the state from.
Permission change The access predicate is edited; an evaluate entry is added, carrying the item's new term set inline. Not until compaction folds it, and in neither direction until then. The compaction fold, which stamps a fold epoch f; the entry then retires under the same ledger rule as a deletion's d. A view built before the fold still carries a revoked term (fail-open) and is missing a granted one (wrong counts).

Sources

Every structure and constant on this page traces to the Tessera design corpus: the architecture design (the specification), the concurrency and lifecycle document (generations, pins, the three retirement rules, the write-ahead log), the contracts specification (bundle format and the plugin boundary), and the Phase 0 measurement record. Section references are given inline. Where the two disagree, the contracts specification's recorded deviations govern.

Measured figures were obtained on WSL2, 12 cores, 39 GB, over a real 2.42-million-paper arXiv corpus with synthetic access-control policies, scaled to 109. The measurement record describes its own timings as indicative rather than certified, and that caveat carries here.
