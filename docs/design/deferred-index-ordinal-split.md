# Splitting permanent identity from a renumberable index ordinal

**Status:** Deferred — a sketch, **explicitly not approved**. Recorded so the option is not lost and so its open problems are not rediscovered from scratch. Nobody should treat this as a design; it is the material a design would start from.

**What it would take to become one:** the independent plan review this repo requires before implementation, aimed squarely at the overlay question below — **an ι-space design that cannot answer it is not a candidate** — and then a trigger: a deployment at 10⁸ or above whose fragmentation figure shows the un-banked fraction actually costing authorise budget.

---

**Splitting the permanent identity from a renumberable index ordinal — a sketch to be designed properly, not a decision.** Design §11.1's signature-sorted assignment is scoped to one batch, and r23 records that nothing repairs it within the identity guarantee. This is the shape of the only fix that would recover the full win invisibly, recorded so the option is not lost — **but its central safety argument does not close as first drafted, and the open holes are named below rather than papered over.** Nobody should treat this as approved.

*The shape.* One integer is currently doing two jobs with contradictory requirements: **permanent identity** (I9, `tessera_id`, WAL rows, the external-ID sidecar) and **index position** (contiguity, which the probes call the highest-leverage property in the index). This is precisely the argument §5.1 already makes to justify entity IDs being distinct from row IDs — *no single integer holds both properties* — applied one level down. The sketch gives every entity a bundle-relative **index ordinal** ι alongside its permanent ID: postings, mask fragments and (Phase 3) node memberships and generating sets move to ι-space; `permutation.bin` becomes ι→row. Between compactions ι is appended monotonically, exactly as today; at a forced full compaction it is re-sorted globally by term signature.

*The argument that was supposed to make it safe, and where it fails.* The precedent is that **term IDs are already bundle-relative renumberable ordinals**, made safe by r19's fragment-cache key including the identity of the postings a mask was built from — so a cache holding a stale ι would be invalidated by key rather than by discipline. That much is true for *caches*. It does not reach three things that hold entity-space data and are not caches, and one of them is a **fail-open**:

- **The overlay is the fail-open.** Lifecycle §5.3 requires compaction to carry forward *verbatim, not folded* the post-snapshot tombstones, the active suppression set and every unfolded overlay entry, and SA §6.5's deny-retirement rule keeps deny entries alive across many compactions by design. If overlay entries were keyed by ι and a compaction renumbered ι, verbatim carry-forward would re-point every deny at a **different entity** — the suppressed item becomes visible and an innocent one is denied. This is the retirement-rule failure class the corpus has already caught twice. The obvious repair is to key the overlay in identity space, but then I1's composition mixes an ι-space fragment with an identity-space `L` on every request and needs a translation this sketch does not specify or price. **Unresolved.**
- **The WAL records allocated entity IDs** and replay reuses them (SA §6.2) — it is not a cache and no key invalidates it. Note the disanalogy with the term-ID precedent, which is what made that precedent look stronger than it is: term IDs are renumbered only at a *full build*, which emits a fresh prefix and rewrites everything, and WAL `Change` records are expressed in *caller* space so replay re-interns. Renumbering at compaction has neither property.
- **`ext-locator.u32` is indexed by entity ID** (contracts §2.4) and would need rewriting or reinterpreting.

*What it would cost, corrected.* **Two** `u32` arrays, not one — ι→identity so the gather can still emit a stable `tessera_id` (C17, §10.6, contracts §2.2), and identity→ι for ingest, overlay lookup and external-ID resolution: 8 GB at 10⁹, not 4. The remap pass is O(postings **+ memberships + generating sets**), all three of which this sketch moves. **I8** ("a label's generating set is immutable once supplied") needs the same explicit treatment the sketch demands for I9: renumbering rewrites generating-set *contents* while preserving membership, which is representation-only but must be argued, not assumed. And §11.3's re-rank decorator is a **row-space Morton** re-rank bounded by a 5 GB maximum merged segment — a *global* ι re-sort is only available at forced full compaction, which at 10⁹ costs about what the escape-hatch rebuild costs, so "recovers the full figure permanently" is contingent on paying that. The unambiguous benefit is that ι-space stays dense, so postings, memberships and the permutation stop paying design §16's consumed-versus-live gap.

*What would have to happen first.* The plan-review treatment CLAUDE.md prescribes, aimed squarely at the overlay question — an ι-space design that cannot answer it is not a candidate. Then a trigger: a deployment at 10⁸ or above whose `/control/status` fragmentation figure (contracts §3.4) shows the un-banked fraction actually costing authorise budget. Nothing forecloses it meanwhile — r19's cache keys, an unpublished bundle format and an out-of-contract WAL are preconditions that exist for other reasons. It composes with signature-major row layout below: under ι, `ι → row` becomes near-monotone within a signature group, strengthening that item's permutation-encodability leg.

*The escape hatch, documented and deliberately not built.* A deployment that can tolerate a caller-visible identity break can recover 100% of the figure with no engine machinery at all: rebuild with entity IDs reassigned in global signature order and advance the idset, exactly as §12.5's repartitioning already does. The recovery path is already specified — consumers persist `external_id` and re-resolve (contracts §2.2) — and the idset check already exists on the request path. It is rejected as the *default* because it breaks the bookmark-and-share property §10.6 and C17 exist to provide, not because it is unsound; for a pre-launch or single-consumer deployment it is the cheapest answer by a wide margin.
